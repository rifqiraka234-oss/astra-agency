# Rebuild HubSpot's core in Astra's own Postgres

Astra's custom CRM should copy HubSpot's object model almost exactly and copy almost nothing of Salesforce's machinery. That means organizations, contacts, a separate lead record with its own five stage pipeline, deals on a stage table that drives probability, many-to-many activities and tasks, and a project and ticket layer for after the sale. Then it should add three things neither vendor gives a small agency: per-thread lemlist reconciliation, an approval gate on every outbound message, and invoices drafted in the CRM but numbered and issued by Moneybird. The recommended build is about 25 core tables plus a platform layer. Real columns hold the fields everyone uses, a JSONB `custom` column driven by a `field_definitions` table holds admin-added fields, and hard unique indexes on normalised email and registrable domain do the dedup. An append-only `stage_transitions` table and a trigger-written `audit_log` replace HubSpot's hundreds of "date entered stage" properties. Every external record resolves through an `external_ids` table, and every connector resumes from a `sync_cursors` row. The case for building is strong: today's "CRM" is a 3,181 row append-only JSONL file with **106 distinct status values, 107 distinct keys and 154 rows with no lemlist `contactId`** (measured on `state/silent_accepted_queue.jsonl`, 2026-11-06). Even good tooling around it can't answer "who have we actually spoken to" without going back to lemlist thread by thread. The MVP should be the sales core plus lemlist and Gmail ingestion. Automations and dashboards come second, projects, quotes and invoicing third, and tickets with a client portal and a public API last. One caveat runs through the whole report: HubSpot's documentation was fetched and read directly, but Salesforce's developer and help sites returned HTTP 403 or empty JavaScript shells. Every Salesforce field list below is therefore marked as prior knowledge or search summary, and every schema and default stage list is a design recommendation (inference) unless a citation says otherwise.

## The JSONL files show exactly what a CRM must fix

The brief described the current queue file as 3,095 rows for 696 people across about 40 inconsistent field names. A recount on 2026-11-06 found it has grown to **3,181 rows, 594 distinct lemlist contactIds plus 154 rows keyed only by leadId or name, and 107 distinct keys, 65 of which appear on fewer than 50 rows**. The status column alone holds **106 distinct values**, from `SENT` (500 rows) and `DRAFTED` (451) to `NUDGED`, `FINAL_CLOSE_DRAFTED`, `CLOSED_NOT_ICP` and `SAID_YES_PENDING`. That is the classic failure a CRM schema exists to prevent. One field mixes the pipeline stage, the research state, the disqualification reason and the outreach step, so no query can tell them apart, and "the latest row per leadId is authoritative" is a convention a reader has to remember rather than a constraint the database enforces.

The second constraint comes from the system of record itself. The repo's own live tests found that lemlist's `type=linkedinInviteAccepted` activity count matched the campaign metric exactly at 320, while `type=linkedinSent` returned 298 records, 260 of which were connect notes, and missed known sends. Messages sent by hand from the lemlist inbox carry `campaignId: null` and are not attached to the lead's activity history (`docs/lemlist-field-index.md`, sections 6.1 to 6.4). The per-contact thread route pages **10 messages per page, newest first**, and splits text across a `message` and a `text` field. Any sync design that trusts bulk activities will repeat the false all-clears this repo has already paid for. So the CRM must treat lemlist webhooks as a fast hint and a per-contact thread pull, reconciled against `totalItems`, as the truth. Both are designed in the email and lemlist section below.

## Twelve core objects cover everything Astra asked for

HubSpot's sales model is Company, Contact, Deal and, since 2024, a separate Lead object. Each has a small set of user-entered fields plus many system-calculated rollups such as last activity, association counts, revenue totals and stage timestamps ([HubSpot company properties](https://knowledge.hubspot.com/properties/hubspot-crm-default-company-properties); [HubSpot deal properties](https://knowledge.hubspot.com/properties/hubspots-default-deal-properties)). The single most useful design lesson is to store the user-entered fields as columns and **derive every calculated field from activity, stage history and association tables**, so nobody can type a wrong "last contacted" date. Salesforce instead converts a flat Lead into Account, Contact and Opportunity and freezes the lead ([Salesforce convertLead, search summary](https://developer.salesforce.com/docs/atlas.en-us.api.meta/api/sforce_api_calls_convertlead.htm)). That model duplicates data when contacts already exist, and Astra's do, because lemlist creates them before any qualification. HubSpot's approach suits Astra better: a lead is a pipeline record attached to an existing contact and organization ([HubSpot Leads API](https://developers.hubspot.com/docs/api-reference/crm-leads-v3/guide)).

### Default fields worth copying, object by object

The table lists what to store and what to compute. HubSpot fields come from fetched KB pages. Salesforce equivalents are from prior knowledge because the Object Reference returned 403, so treat them as a checklist to verify, not as quotation. Astra-specific additions are inference.

| **Line item and product** | name, SKU, unit price, quantity, discount, tax rate, billing frequency, term, billing start date ([HubSpot line items](https://knowledge.hubspot.com/properties/hubspots-default-line-item-properties)) | net price, tax amount, MRR, ARR, TCV | snapshot of name and price at sale |

Quotes, invoices, contracts, activities, meetings and email messages complete the twelve, and they are covered in the sections that follow. Two HubSpot details are worth copying on purpose. HubSpot keeps **two different definitions** of recency: "Last contacted" counts only outbound one-to-one touches such as calls, emails, meetings and LinkedIn messages, while "Last activity date" also counts notes and completed tasks ([HubSpot contact properties](https://knowledge.hubspot.com/properties/hubspots-default-contact-properties)). Astra needs both, plus a separate `last_inbound_at`, because "is it our turn" (their message is the latest and has real content) is the key triage field in the inbox routine. HubSpot also keeps the contact's free-text "Company name" separate from the associated company record, so it drifts after a job change ([HubSpot contact properties](https://knowledge.hubspot.com/properties/hubspots-default-contact-properties)). The custom build should drop that duplicate field entirely.

### Associations carry roles, and job history needs dates

HubSpot treats every link as a directional many-to-many association that can carry one or more labels, and "if a record has more than one associated company, only one can be the primary company" ([HubSpot Associations v4](https://developers.hubspot.com/docs/api-reference/crm-associations-v4/guide)). Salesforce has the richer history model. Its AccountContactRelation carries a Roles multipicklist (Decision Maker, Economic Buyer, Influencer, Technical Buyer and others), `IsDirect` for the primary account, `IsActive`, and `StartDate` and `EndDate` "to keep a history of the relationship" ([Salesforce AccountContactRelation, search summary](https://developer.salesforce.com/docs/atlas.en-us.object_reference.meta/object_reference/sforce_api_objects_accountcontactrelation.htm)). The open-source Postgres CRMs are simpler. Twenty keeps one nullable `companyId` per person and attaches tasks, notes, emails and calendar events through `*_target` junction tables ([Twenty person entity](https://github.com/twentyhq/twenty/blob/main/packages/twenty-server/src/modules/person/standard-objects/person.workspace-entity.ts)), and Attio's People also have a single `company` reference, auto-set from the email domain ([Attio People](https://docs.attio.com/docs/standard-objects/standard-objects-people)).

Astra needs Salesforce's version, and its own playbook says why. Two of the first five accepted leads reviewed on 2026-09-22 carried a lemlist company the person no longer owned or never owned. One had sold the company and his tagline said "Former Owner". Another had a multinational's domain, and a third was CEO of a programme inside a charity (CLAUDE.md, "Reconcile the record against itself"). The recommendation (inference) is a `contact_org_roles` junction with `relationship` (owner, founder, employee, advisor, former_owner), `title`, `is_primary`, `is_current`, `start_date`, `end_date`, `evidence_url` and `verified_at`, plus `contacts.primary_org_id` as a fast default. A job change then closes one row and opens another, and deals and activities keep pointing at the organization where they happened. Deal participants get a `deal_contacts` junction with a role (decision maker, champion, billing contact) and `is_primary`, which is Salesforce's OpportunityContactRole shape (prior knowledge, unverified). A small `association_labels(from_object, to_object, label, inverse_label)` lookup reproduces HubSpot's paired labels without a generic association table.

## Pipelines, activities and tasks run the daily work

### Stage tables drive probability, and history is a log

HubSpot's default deal pipeline runs **Appointment scheduled 20%, Qualified to buy 40%, Presentation scheduled 60%, Decision maker bought-in 80%, Contract sent 90%, Closed won 100%, Closed lost 0%**. Both a won and a lost stage must exist for sales reports to work, and every non-deal stage is flagged Open or Closed ([HubSpot pipelines](https://knowledge.hubspot.com/object-settings/set-up-and-customize-pipelines)). Stages can require fields on entry through conditional logic. Pipeline rules can block skipping stages and moving backward, but users can always jump to Closed won or Closed lost and reopen from a closed stage ([HubSpot pipeline rules](https://knowledge.hubspot.com/object-settings/set-up-pipeline-rules)). HubSpot stores stage history as "Date entered", "Date exited" and "Time in current stage" properties per stage ([HubSpot deal properties](https://knowledge.hubspot.com/properties/hubspots-default-deal-properties)). Salesforce stores it as OpportunityHistory rows that snapshot stage, probability, amount, close date and forecast category after each change ([Salesforce field reference, OpportunityHistory](https://developer.salesforce.com/docs/platform/field-reference/references/field-reference/salesforce-field-reference-opportunityhistory.html)). The Salesforce shape is the right one for Postgres. One append-only `stage_transitions` table, holding the record, the from and to stages, the amount and close date snapshot, the actor and the source, gives date entered, date exited, cumulative time in stage, velocity and pipeline-as-of-date reports from a single source, for leads, deals, projects and tickets alike.

HubSpot's lead pipeline is **New, Attempting, Connected, Qualified, Disqualified**. On the default pipeline, logging an email, call or LinkedIn message moves New to Attempting, and a reply, a completed meeting or a connected call moves Attempting to Connected. A manual backward move stops automation for that lead ([HubSpot lead pipeline automation](https://knowledge.hubspot.com/object-settings/set-up-lead-pipeline-automation)). Pipedrive adds a per-stage "Rotting in (days)" threshold, measured from the deal's last update, and flags any deal with no scheduled next activity ([Pipedrive rotting](https://support.pipedrive.com/en/article/the-rotting-feature)). Pipedrive users complain they can't choose which updates reset the clock ([Pipedrive community](https://community.pipedrive.com/discussion/17420/rotting-days-resetting-with-field-updates-or-client-communication)), so the custom build should let Raka choose which activity kinds count.

The defaults below are recommendations fitted to Astra's process as written in CLAUDE.md, not sourced benchmarks, and the probabilities are placeholders until a quarter of stage history gives real rates. Third-party HubSpot guidance makes the same warning about HubSpot's own defaults ([Pedowitz Group](https://www.pedowitzgroup.com/blog/hubspot-pipeline-reporting-blog)).

| Pipeline | Stages (closed stages in bold) | Separate status or reason fields |
|---|---|---|
| **Lead (prospecting)** | New (imported or accepted), Researching, Attempting (opener sent), Connected (real reply), **Qualified** (meeting or prototype yes, creates deal), **Disqualified** | `research_status` (unresearched, drafted, awaiting approval, sent), `disqualify_reason` (no strong angle, blocked needs info, do not contact, not ICP, former owner, wrong company), `linkedin_accepted_at` as a dated event so "Silent accepted" is a query, not a stage |
| **Sales (new business)** | Discovery booked 15%, Prototype or brief agreed 30%, Prototype sent 40%, Proposal sent 60%, Negotiation 75%, Contract sent 90%, **Won 100%**, **Lost 0%** | required `lost_reason` on Lost, `forecast_category`, `next_step` |
| **Existing business** | Opportunity spotted, Proposal sent, Contract sent, **Won**, **Lost** | `deal_type` = upsell, renewal or expansion |
| **Project delivery** | Kickoff, Design, Build, Review and QA, Launched, **Closed** | `health` (on track, at risk, off track), `status` (active, on hold, cancelled) kept apart from stage |
| **Tickets** | New, Waiting on us, Waiting on client, **Closed** (HubSpot's support defaults, [HubSpot pipelines](https://knowledge.hubspot.com/object-settings/set-up-and-customize-pipelines)) | `pauses_sla` flag on Waiting on client |

Lifecycle stage on organizations and contacts should be derived and forward-only: lead, opportunity once an open deal exists, customer once a deal is won. HubSpot's defaults follow the same logic and its automation "will only move the stage forward" ([HubSpot lifecycle stages](https://knowledge.hubspot.com/records/use-lifecycle-stages)). A deal amount validation rule warning outside the quotable €500 to €50,000 band from CLAUDE.md is a cheap guard worth adding (inference).

### One activity table, linked many-to-many

HubSpot stores every email, call, meeting, note, task and "communication" (LinkedIn, SMS, WhatsApp) as an engagement associated with any number of records. LinkedIn messages use `hs_communication_channel_type` = `LINKEDIN_MESSAGE` ([HubSpot Communications API](https://developers.hubspot.com/docs/api-reference/latest/crm/objects/communications/guide)). By default, activity logged on a contact also lands on the contact's primary company and its **five most recent open deals**. When a contact moves company, past activity stays with the old company ([HubSpot activity association](https://knowledge.hubspot.com/records/associate-activities-with-records)). Salesforce splits the person link (WhoId, contact or lead) from the thing link (WhatId, account, opportunity or custom) on Task ([Salesforce Task field reference, search summary](https://developer.salesforce.com/docs/platform/field-reference/references/field-reference/salesforce-field-reference-task.html)), and Salesforce's Einstein Activity Capture is the cautionary tale. For years captured email sat in a separate store that showed on the timeline but could not be reported on, queried or used in automation, until Summer '25 added an option to write it as native records ([asagarwal.com, secondary](https://www.asagarwal.com/?p=32826); [Revenue Grid, vendor](https://revenuegrid.com/blog/einstein-activity-capture-limitations/)).

The recommendation (inference) is one `activities` table with `kind` (email, linkedin_message, linkedin_invite, linkedin_accept, call, meeting, note, stage_change, artifact_sent, system), `direction` (outbound, inbound, internal), `occurred_at`, `actor`, `body`, `meta jsonb`, and a `UNIQUE (source, external_id)` constraint so every sync is idempotent. Links go in `activity_links` with nullable typed foreign keys to contact, organization, lead, deal, project and ticket, one non-null per row, plus `is_primary`. That keeps referential integrity, which a polymorphic `entity_type, entity_id` pair loses, and still gives HubSpot's many-to-many reach. Copy the HubSpot auto-association rule at write time (contact, then primary organization, then open deals for that organization) so the timeline survives a later job change. Meetings get their own detail columns: `meeting_type` (discovery, prototype review, proposal, kickoff, project check-in, QBR, renewal), `calendar_event_id`, and `outcome` with HubSpot's values scheduled, completed, rescheduled, no show and canceled ([HubSpot activity properties](https://knowledge.hubspot.com/properties/hubspots-default-activity-properties)). A completed outcome should advance the linked lead and trigger the meeting brief that CLAUDE.md already requires.

### Tasks with owner, due date, recurrence and per-person views

A HubSpot task has a title, a type (To-do, Call, Email, plus LinkedIn Sales Navigator InMail and connection request), priority Low, Medium or High, a due date with time, an email reminder, an assignee, an optional queue, notes, associations to any records, and a "repeat every N days, weeks, months or years" setting. **The next instance is created when the previous one is completed, deleted or goes overdue** ([HubSpot create tasks](https://knowledge.hubspot.com/tasks/create-tasks)). The API exposes status as `NOT_STARTED` or `COMPLETED` and records no completion timestamp ([HubSpot Tasks API](https://developers.hubspot.com/docs/api-reference/crm-tasks-v3/guide)). Salesforce stores the due date as a date with no time and a separate ReminderDateTime ([Salesforce Task, search summary](https://developer.salesforce.com/docs/platform/field-reference/references/field-reference/salesforce-field-reference-task.html)).

Astra's task table (inference) should carry `title`, `body`, `type` (todo, call, email, linkedin_message, linkedin_nudge, meeting_prep, send_artifact, checkin, renewal, invoice_followup), `priority`, `status` (not started, in progress, waiting, completed, cancelled), `due_at`, `all_day`, `owner_user_id`, `queue_id`, `recurrence_rule` (an RRULE string, so "first Monday every quarter" works), `recurrence_parent_id`, `completed_at`, `completed_by` and `created_from` (manual, workflow, recurrence, stage entry, import). Links go in `task_links`, which mirrors `activity_links`. Luna's and Josh's task lists are then saved views over `owner_user_id` with Overdue, Today, This week and Future tabs. Overdue is a filter (`status` open and `due_at < now()`), never a stored flag. Reminders are rows in a `reminders` table (`task_id` or `record`, `remind_at`, `channel`, `sent_at`) polled by a worker, which covers account check-ins, renewals and invoice chases with one mechanism. Copy HubSpot's "prompt for a follow-up task on completion" but suppress it on closed records, the exact complaint Pipedrive users raise ([Pipedrive community](https://community.pipedrive.com/discussion/comment/17159)).

### Email and lemlist: fast hints, slow truth

For Gmail on Astra's own Workspace, the cheapest compliant path is an OAuth app marked **Internal**. Google lists internal use ("only used by people in your Google Workspace or Cloud Identity organization") among the cases where verification is not needed ([Google Cloud verification exemptions](https://support.google.com/cloud/answer/13464323?hl=en)). One caution belongs here. `gmail.readonly` and `gmail.modify` are restricted scopes and storing restricted data on servers triggers a security assessment for public apps ([Gmail API scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)), and a Google brand-verification page reportedly says restricted scopes still need verification ([Google brand verification, search summary](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification)). Confirm with Google before the app ever touches a client's domain. Sync follows Google's documented pattern. A full sync runs `messages.list` and `messages.get` and stores the latest `historyId`. Incremental sync runs `history.list` from that id, and an out-of-range id returns **HTTP 404, which means full resync** ([Gmail sync guide](https://developers.google.com/workspace/gmail/api/guides/sync)). Push arrives through Pub/Sub `users.watch`, which must be renewed at least every 7 days (Google recommends daily) and delivers at most one event per second per user, with excess dropped, so a periodic `history.list` fallback is required ([Gmail push guide](https://developers.google.com/workspace/gmail/api/guides/push)). Replies sent from the CRM must set `threadId`, RFC 2822 `In-Reply-To` and `References`, and a matching Subject ([Gmail messages resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages)). Quota is not the constraint (`messages.send` costs 100 units against 6,000 per user per minute) ([Gmail quota](https://developers.google.com/workspace/gmail/api/reference/quota)). Workspace's **2,000 messages and 2,000 unique external recipients per user per day** are the ceiling ([Workspace sending limits](https://knowledge.workspace.google.com/admin/gmail/gmail-sending-limits-in-google-workspace)).

Store each email once as an `email_messages` row with both the mailbox-scoped Gmail `id` and `threadId` and the global RFC822 `Message-ID`, so a CC between Raka and Luna logs once. Participants go in `email_participants(message_id, role, address, contact_id)`, mirroring Salesforce's EmailMessageRelation (search summary). Opens and clicks go in a separate `email_events` table, following HubSpot's split between logging a copy and tracking engagement ([HubSpot open and click tracking](https://knowledge.hubspot.com/connected-email/understand-hubspot-sales-email-open-and-click-tracking)). Open tracking should be **off by default** for cold one-to-one sends. Apple Mail Privacy Protection prefetches tracking pixels, and vendor estimates put inflated opens at roughly half or more of reported opens ([Validity, vendor](https://www.validity.com/blog/case-closed-the-mystery-of-declining-email-open-rates/)), so replies are the engagement metric. A `never_log` list of addresses and domains, checked before insert, copies HubSpot's privacy valve ([HubSpot add-in settings, search summary](https://knowledge.hubspot.com/connected-email/customize-your-hubspot-sales-office-365-add-in)).

lemlist's API uses Basic auth with the key as password and allows **20 requests per 2 seconds** per key ([lemlist rate limits](https://developer.lemlist.com/api-reference/getting-started/rate-limits.md)). Its webhooks cover about 80 event types including `linkedinInviteAccepted`, `linkedinReplied` and `emailsReplied`. They authenticate only with a **plain shared secret in the JSON body, with no HMAC**, document no retry policy, and are **disabled when the endpoint returns 404 or 410** ([lemlist Add Webhook](https://developer.lemlist.com/api-reference/endpoints/webhooks/add-webhook)). Since 30 March 2026, unsubscribes emit `entityUnsubscribed` and `variableUnsubscribed` ([same page](https://developer.lemlist.com/api-reference/endpoints/webhooks/add-webhook)). The design (inference) is one all-events webhook to an unguessable path. It checks the secret in constant time, writes the raw payload to `inbound_events` with a unique `(source, external_event_id)`, returns 200 fast, and returns 503 rather than 404 during deploys. Every event then enqueues a **per-contact thread pull** that pages until `nextPage` is null and checks the count against `totalItems`, the method `tools/lemlist.py thread` already implements (CLAUDE.md). A scheduled reconciler sweeps `linkedinInviteAccepted` by `minDate` cursor and re-pulls threads for any contact with recent activity, which covers hand-sent inbox messages that never appear in activities. Connect notes are identified by `emailTemplateName = linkedinInvite`, not by body length (`docs/lemlist-field-index.md`).

Draft-before-send needs a table of its own, because it is Astra's hardest rule and no benchmark has it (inference). An `outbound_messages` row moves from `draft` to `awaiting_approval` to `approved` (with `approved_by`, `approved_at` and the approval words verbatim) to `sent`. The send worker refuses any row without an approval record, and it re-pulls the thread immediately before sending and refuses if the thread changed since the draft. That moves CLAUDE.md's "his explicit word every single time" from a habit into a constraint.

## Projects, tickets and invoices finish the account lifecycle

### Projects and retainers come out of the won deal

HubSpot's Projects object has a name, description, status, type, target due date, owner, and a required pipeline and stage, with associations to contacts, companies, deals and tasks ([HubSpot Projects API](https://developers.hubspot.com/docs/api-reference/latest/crm/objects/projects/guide)). The KB shows a deal workflow that creates a project when a deal reaches Closed won, references the statuses On Track, Delayed and On-Hold, and documents **no native budget, hours or time tracking** ([HubSpot projects KB](https://knowledge.hubspot.com/records/understand-and-use-projects-object)). Agency tools such as Productive fill that gap with fixed, hourly, mixed and recurring retainer budgets, invoices built from unbilled time, and reminders when a retainer is ready to invoice ([Productive billing](https://productive.io/billing/)). Salesforce has no core project object (prior knowledge). Astra's model (inference) is `projects` with `kind` = prototype or delivery, because a prototype is a pre-sale project tied to a lead or deal and today lives as `promisedConcept`, `angleNumber`, `netlifyUrl` and `outcome` in `state/prototypes.jsonl`. Children are `project_milestones` (which double as billing triggers on fixed-price work), project-linked tasks, and `time_entries` with `billable` and `invoice_line_id`, so "unbilled" is simply billable time with no invoice line. Retainers, hosting and maintenance live in `contracts` (`start_date`, `end_date`, `renewal_date`, `notice_period_days`, `auto_renew`, `monthly_fee`, `included_hours`, `sla_policy_id`) with monthly `retainer_periods`. That one table feeds renewal reminders, ticket SLAs and MRR.

### Tickets need SLA clocks and a portal that shows more than tickets

HubSpot's ticket is thin: name, description, pipeline, status, priority, category, source and owner. The bulk of its fields are computed timing fields (date entered and exited per status, time to first response, time to close, each also "in SLA hours") plus four SLA fields whose status takes five values: **Active SLA, Due soon, Overdue, SLA completed on time, SLA completed late** ([HubSpot ticket properties](https://knowledge.hubspot.com/properties/hubspots-default-ticket-properties)). Business hours change the answer materially. A ticket opened Monday 17:00 and answered Tuesday 10:00 shows a 2-hour first response, not 17 hours ([HubSpot Community](https://community.hubspot.com/t/slas-and-office-hours/121874)). HubSpot's customer portal is Service Hub Professional and above, and **shows tickets only** ([HubSpot customer portal](https://www.hubspot.com/products/service/customer-portal); [third-party setup guide](https://knowledge.thegistinbound.com/how-to-configure-a-customer-portal-in-hubspot)). That gap is one an agency portal can beat. The recommendation (inference) is a `tickets` table with a human number (T-2026-0042), a `ticket_status_events` log from which all timings derive, a `business_calendars` table in Europe/Amsterdam with Dutch holidays, and a `business_minutes_between()` function that skips statuses flagged `pauses_sla`. SLA targets come from the contract tier times priority, not from priority alone. The portal uses magic-link login scoped to `portal_users(contact_id, organization_id, role)` and shows the client's tickets, project milestones and invoices.

### Invoices: draft in the CRM, issue in Moneybird

The legal surface is the deciding factor. Article 226 of the VAT Directive requires, among other things, the issue date, "a sequential number, based on one or more series, which uniquely identifies the invoice", both VAT numbers where reverse charge applies, the full names and addresses of supplier and customer, the extent and nature of services, the supply date, the taxable amount per rate, the rate and VAT amount, and the words "Reverse charge" where the customer is liable ([Directive 2006/112/EC Art. 226, legislation.gov.uk copy](https://www.legislation.gov.uk/eudr/2006/112/article/226); EUR-Lex was unreachable). The Dutch government adds the KVK number. It requires that each number occur only once in sequence, that the invoice be sent **by the 15th of the month after supply**, and that it be kept **7 years**. It notes that a PDF is not an e-invoice and that **domestic B2B e-invoicing becomes mandatory on 1 July 2030** ([Ondernemersplein](https://ondernemersplein.overheid.nl/wetten-en-regels/facturen-maken-en-versturen/)). Cross-border intra-EU B2B e-invoicing under ViDA also starts 1 July 2030. **Belgium has required Peppol B2B e-invoices since 1 January 2026**, and Germany has required receipt since 2025 with issuing phased in for 2027 and 2028 ([eConnect ViDA timeline, a Peppol vendor](https://econnect.eu/en/docs/knowledge/regulations/europe/vida/timeline)).

So the CRM should own the commercial truth: products, quotes, accepted line items, billable time, retainer usage and what is due to invoice. It should **hand legal issue to accounting software**. Moneybird's API fits. Drafts carry a `draft_id` and get their legal `invoice_id` (for example 2026-0001) only when sent. Invoices can be looked up by a `reference` that holds the CRM's id, and a synchronization endpoint returns ids and versions for cheap state mirroring. States run draft, scheduled, open, pending_payment, reminded, late, paid and uncollectible. UBL download and credit notes via `duplicate_creditinvoice` are built in ([Moneybird sales invoices API](https://developer.moneybird.com/api/sales_invoices/)). The CRM keeps `invoices` with `external_id`, `external_number`, `state` and `due_date` mirrored, so overdue chasing, AR ageing and health scoring work without the CRM ever minting a number. If Astra ever issues invoices itself (inference): use a `invoice_number_sequences` row locked with `SELECT ... FOR UPDATE` in the same transaction that flips draft to issued, because Postgres sequences skip values on rollback. Block updates to financial columns once `issued_at` is set, correct only with credit notes, and store the rendered PDF and its hash. VAT treatment (NL 21%, EU B2B reverse charge with a stored VIES check, outside scope) belongs on each invoice as an enum. The non-NL rules are background knowledge, not verified this session, and an accountant should sign them off.

## The platform layer makes it a CRM rather than a database

### Custom fields as metadata plus JSONB

HubSpot's property model is a few storage types dressed as many field types. Its settings include an internal name that **cannot be edited** after creation, groups, per-property view and edit access, validation (regex, unique, min and max, date windows), and unique-value properties capped at **10 per object, settable only at creation** ([HubSpot create and edit properties](https://knowledge.hubspot.com/properties/create-and-edit-properties); [HubSpot validation rules](https://knowledge.hubspot.com/properties/set-validation-rules-for-properties)). Twenty goes further and runs real DDL per workspace from a `fieldMetadata` table, but a 2024 code review flags dynamic schema assembly and workspace migrations as its riskiest, least tested parts ([Codeline review of Twenty](https://www.codeline.co/thoughts/repo-review/2024/twenty-open-source-crm)). Attio historises every value with `active_from` and `active_until` ([Attio attribute types](https://docs.attio.com/docs/attribute-types)). For one workspace with a few dozen custom fields, the recommendation (inference) is a `field_definitions` table (`object_type`, immutable `internal_name`, `label`, `group`, `field_type`, `options`, `validation`, `is_required`, `is_unique`, `is_sensitive`, `default_value`, `archived_at`) and a `custom jsonb not null default '{}'` column on each object keyed by internal name. Index it with one `GIN (custom jsonb_path_ops)`, which Postgres documents as "usually much smaller" and faster for containment ([PostgreSQL JSON types](https://www.postgresql.org/docs/current/datatype-json.html)), plus a btree expression index created when an admin marks a field sortable. A unique custom field gets a partial unique expression index, created only after a duplicate check. That is the same reason HubSpot restricts uniqueness to creation time. Validation runs in one server-side function shared by the UI, the import path and the API, because HubSpot's own rules are not enforced in workflows ([HubSpot validation rules](https://knowledge.hubspot.com/properties/set-validation-rules-for-properties)).

### Dedup by email and domain, enforced in the database

HubSpot dedups contacts on email and companies on primary domain, blocks manual duplicates with an "already exists" alert, and matches imports on primary and secondary domains. It explicitly does **not** dedup companies created through the API or by sync apps ([HubSpot deduplication](https://knowledge.hubspot.com/records/deduplication-of-records)). Domains are stored as root domains without protocol, www or path, and each subdomain counts as a separate company ([HubSpot multiple domains](https://knowledge.hubspot.com/records/add-multiple-domain-names-to-a-company-record)). For free-mail addresses HubSpot falls back to the contact's website URL and otherwise makes no company match ([HubSpot auto-association, search summary](https://knowledge.hubspot.com/object-settings/automatically-create-and-associate-companies-with-contacts)). Its merge keeps the primary's value unless that value is empty, combines timelines and associations, keeps the furthest lifecycle stage, turns the loser's email into a secondary email, and **cannot be undone** ([HubSpot merge records](https://knowledge.hubspot.com/records/merge-records)). Salesforce pairs matching rules (exact or fuzzy, for example Jaro-Winkler on first name with a threshold of 85) with duplicate rules that block, allow or alert, and merges at most three records at once ([Salesforce matching methods, search summary](https://help.salesforce.com/s/articleView?id=sf.matching_rules_matching_methods.htm&language=en_US&type=5); [Salesforce merge, search summary](https://developer.salesforce.com/docs/atlas.en-us.208.0.api.meta/api/sforce_api_calls_merge.htm)).

The API gap is the lesson: uniqueness has to live in the database, not the UI (inference). Use `contact_emails` with a unique index on `lower(trim(email))`, because a plain text unique constraint is case sensitive. Postgres now suggests nondeterministic collations over `citext` ([PostgreSQL citext](https://www.postgresql.org/docs/13/citext.html)), but an open bug report from August 2026 shows a differently collated unique index bypassing one ([pgsql-bugs #19646](https://www.postgresql.org/message-id/19646-b1cfc299badcbd7e@postgresql.org)), so `lower()` is the safer choice today. Use `organization_domains` with a unique normalised registrable domain (scheme, www, path and port stripped, IDN to punycode, then reduced with the Public Suffix List in app code, which was not verified this session). Add a unique normalised `linkedin_url` on contacts, because most of Astra's prospects arrive from LinkedIn with no email at all. Finally, keep an editable `free_mail_domains` blocklist. Manual create runs a live duplicate check on blur and offers "open existing". A nightly `pg_trgm` similarity job proposes fuzzy pairs, and rejected pairs are stored so they don't resurface. Merge copies HubSpot's rules, but a `merge_log` with a JSON snapshot of the losing record and a `merged_record_ids` table make unmerge possible, which HubSpot cannot do.

### Import and export that can be reverted

HubSpot imports CSV, XLSX and XLS with one sheet and a header row. It auto-suggests the column mapping, matches on email, domain, record ID or a custom unique property, and creates, updates or both. **Blank cells never clear values**, a leading semicolon appends to a multi-select, owners map by email, and one file can carry several objects and their associations ([HubSpot import files](https://knowledge.hubspot.com/import-and-export/set-up-your-import-file); [HubSpot import tool](https://knowledge.hubspot.com/import-and-export/understand-the-import-tool)). Its undo only deletes records an import created. Updates need the separate "restore CRM changes" tool, which reaches back 14 days ([HubSpot past imports](https://knowledge.hubspot.com/import-and-export/view-and-analyze-previous-imports)). Pipedrive and Salesforce both use "export with IDs, edit, re-import" for bulk updates, and Salesforce upserts on a field flagged as an external ID ([Pipedrive spreadsheet updates, search summary](https://support.pipedrive.com/en/article/updating-pipedrive-data-with-a-spreadsheet)). The design (inference) runs imports as jobs. An `import_jobs` row stores the mapping, match key, mode and blank handling. `import_rows` stores per-row status and errors, with a downloadable error CSV. Every touched record is tagged with `import_id`, and because the audit log keeps before-images, **reverting an import can delete created records and restore updated values**, beating HubSpot's partial undo. Export is any saved view (filters and columns) to CSV or XLSX, always including record IDs, so the round trip works. Exports are logged as their own audit action.

### Automations on an outbox and a Postgres job queue

HubSpot workflows have five trigger families: event, filter, webhook, schedule or date property, and manual. Event triggers cannot detect non-occurrence because "it is not possible to determine if an event did not occur" ([HubSpot enrollment triggers](https://knowledge.hubspot.com/workflows/set-your-workflow-enrollment-triggers)). The action catalogue covers delays, branches, record edits, create record, task and note actions, association actions, owner rotation, notifications, and custom code and webhooks, which need **Data Hub Professional** ([HubSpot workflow actions](https://knowledge.hubspot.com/workflows/choose-your-workflow-actions)). Logs are kept 90 days. Transient errors retry automatically, and a slow webhook can execute, get logged as failed, retry, and "lead to duplicate effects" ([HubSpot workflow errors](https://knowledge.hubspot.com/workflows/troubleshoot-common-workflow-errors?no_head=1)). Salesforce's transferable idea is the split between before-save field updates, which touch only the triggering record and run much faster, and after-save actions with scheduled paths and one asynchronous path for callouts ([salesforcetime.com, 2022, secondary](https://salesforcetime.com/2022/02/04/record-triggered-flow-before-save-vs-after-save/)).

The engine design (inference, built on documented libraries) follows from that split. Synchronous derivations (weighted amount, stage timestamps, domain normalisation) run in the same transaction. Every record change also writes a `domain_events` outbox row holding the changed fields and their old and new values. A Postgres queue fans those rows out to workflows. graphile-worker gives LISTEN/NOTIFY latency "typically under 3ms", a `job_key` for dedup and replacement, 25 retries with exponential backoff over about 3 days, cron, and jobs added from SQL triggers ([graphile-worker](https://worker.graphile.org/docs)). pg-boss adds dead-letter queues, debounce and throttle policies, and transactional job creation through ORM adapters ([pg-boss](https://github.com/timgit/pg-boss)). Either suffices at agency scale, and neither Temporal nor n8n is needed. The tables are `workflows`, immutable `workflow_versions`, `workflow_enrollments` (unique per workflow and record unless re-enrollment is allowed, copying HubSpot's default of enrolling once) and `workflow_step_runs` with input, output, error and attempt. "Has not happened" rules (no activity in 14 days, close date passed, invoice overdue) run as an hourly sweep through the same enrollment path, and rotting is a derived field, not a workflow. Changes a workflow makes carry `actor = workflow:<id>`, with a hop cap for loop protection. External actions send `step_run_id` as an idempotency key. Ship these as templates: lead replied moves the lead to Connected and creates a reply task for the owner; meeting completed moves it to Qualified and writes the brief; deal won creates the project from a template, a contract for recurring lines, an invoice draft and a notification; renewal date minus notice period minus 30 days creates a renewal task; `next_checkin_date` creates a QBR task; a Moneybird state of `late` creates a chase task for the account manager.

### Roles at HubSpot's size, enforced with row-level security

HubSpot gives each object View, Edit, Delete and Merge scopes of **All, Their team's, Their own, or None**, plus an "Unassigned" toggle. Create is a separate switch that doesn't govern workflow-created records. Export, export approval, bulk delete and audit log access are separate admin permissions, and field-level view and edit restriction is Enterprise ([HubSpot permissions guide](https://knowledge.hubspot.com/user-management/hubspot-user-permissions-guide)). Salesforce layers profiles, permission sets, field-level security, org-wide defaults, a role hierarchy and sharing rules ([Salesforce sharing cheatsheet](https://developer.salesforce.com/docs/atlas.en-us.salesforce_sharing_cheatsheet.meta/salesforce_sharing_cheatsheet/sharing_cheatsheet.htm)), which is overkill for a few users. The recommended model (inference) has four roles. **Owner** (Raka) gets everything, including billing, users, settings, delete, export and the audit log. **Manager** sees and edits all records without user admin. **Member** (Luna, Josh) views all and edits own plus unassigned, with no delete or export. **Contractor** sees assigned records only. A fifth, external role, **portal client**, sees only its own organization. These live in a `permission_grants(role, object_type, action, scope, include_unassigned)` grid, plus `field_permissions` for day rates, margins, cost prices and personal data, enforced in the API layer. Postgres row-level security backs the grid up. With no policy the default is deny, `USING` filters reads and `WITH CHECK` validates writes, and superusers, `BYPASSRLS` roles and table owners bypass it unless `FORCE ROW LEVEL SECURITY` is set ([PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)). Requests therefore run as a non-owner app role with `SET LOCAL app.user_id`, and workers run as a separate system identity so automations aren't silently filtered.

### Audit log, API and webhooks

HubSpot's central audit log covers user actions and shows 30 days of logins in the UI and about 90 through the API. It misses property changes made by forms, the API and integrations ([HubSpot account activity](https://knowledge.hubspot.com/account-management/view-and-export-account-activity-history?authuser=0); [HubSpot community idea thread](https://community.hubspot.com/t5/HubSpot-Ideas/Report-on-Historical-Property-Values-Audit-Trail/idc-p/638104)). A generic `AFTER INSERT OR UPDATE OR DELETE` trigger that diffs `to_jsonb(OLD)` against `to_jsonb(NEW)` and records actor type, actor, source, object, record, action and changes beats that easily (inference). Make it append-only and partition it by month. It serves as field history, the security log for logins, exports and permission changes, and the settings audit trail. For the API, HubSpot's shape is the template. Search uses OR-of-AND filter groups (up to 5 groups, 6 filters each), `limit` up to 200 and an `after` cursor. Batch endpoints take up to 100 records. Upsert matches on a declared unique `idProperty` ([HubSpot search](https://developers.hubspot.com/docs/api-reference/search/guide); [HubSpot contacts API](https://developers.hubspot.com/docs/api-reference/latest/crm/objects/contacts/guide)). HubSpot's v4 webhooks are now a journal that apps poll ([HubSpot webhooks](https://developers.hubspot.com/docs/api/webhooks)). Attio pushes thin events with an HMAC-SHA256 signature, an `Idempotency-Key`, and up to 10 retries over about 3 days ([Attio webhooks](https://docs.attio.com/rest-api/guides/webhooks)). Astra's API (inference) should be REST at `/v1/objects/{type}`, with `/search`, `/batch/{create|update|upsert}` and typed associations. It needs hashed API keys with scopes (`contacts.read`, `email.send`, `webhooks.manage`) and an `Idempotency-Key` table with a 24-hour TTL. Outbound webhooks should follow the **Standard Webhooks** spec: `webhook-id`, `webhook-timestamp` and `webhook-signature` headers, with retries at immediate, 5s, 5m, 30m, 2h, 5h, 10h, 14h, 20h and 24h, and disabling on 410 ([Standard Webhooks spec](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md)). A `GET /v1/events?after=` journal lets a consumer that missed webhooks catch up. That covers Raka building his own connections and Claude routines replacing direct JSONL writes.

### Dashboards: ten fixed widgets before any report builder

HubSpot's custom report builder is Professional and above. It supports up to 12 measures, about a dozen chart types (bar, line, area, combination, donut, pie, KPI, gauge, scatter, pivot, table), a **1,000-row cap on charts and a two-hour auto-refresh** ([HubSpot custom report builder](https://knowledge.hubspot.com/reports/create-reports-with-the-custom-report-builder)). Its funnel reports only work on the built-in stage properties ([HubSpot funnel reports](https://knowledge.hubspot.com/reports/create-custom-funnel-reports?hc_location=ufi)). At agency volume, Postgres views can answer live, so the recommendation (inference) is a fixed set of widgets backed by SQL views, with dashboard-level filters for date range, owner and pipeline. The sales widgets are: open pipeline by stage (count and sum); weighted forecast for the month and quarter against a goal line, with historical stage-to-won rates shown beside the placeholder probabilities; win rate by owner and lead source; average deal size and its trend; median sales cycle and days in stage from `stage_transitions`; a stage conversion funnel built from history so skipped stages count; won and lost by reason. The work widgets are: overdue and due-today tasks per person; rotting deals and leads with no next activity. The money widgets are: invoiced against paid against outstanding with AR ageing buckets (0 to 30, 31 to 60, 61 to 90, 90+), and won-but-unbilled. Astra-specific widgets come from its own routines: the prospecting funnel (accepted to opener sent to reply to meeting to won), the Silent accepted backlog count, replies waiting on us, drafts awaiting Raka's approval, prototypes with a pending outcome older than a week, renewals in the next 60 days, and retainer burn. A single-object report builder (object, ALL or ANY filters, group-by, measure, chart) comes later. Cross-object reporting is the expensive part of HubSpot's builder and can wait.

### GDPR fields belong in the MVP, not the polish phase

B2B prospecting usually rests on legitimate interest under Art. 6(1)(f), which needs a documented test (interest, necessity, balancing), and the EDPB's draft guidelines say direct marketing is not automatically sufficient ([EDPB Guidelines 1/2024 page](https://www.edpb.europa.eu/our-work-tools/documents/public-consultations/2024/guidelines-12024-processing-personal-data-based_en); [Morgan Lewis commentary](https://www.morganlewis.com/blogs/sourcingatmorganlewis/2024/10/gdpr-when-can-data-controllers-rely-on-legitimate-interests-for-data-processing-new-guidelines-from-the-edpb)). Art. 21 gives an absolute right to object to direct marketing, which must be brought to the person's attention "at the latest at the time of the first communication" ([GDPR Art. 21](https://gdpr-info.eu/art-21-gdpr/)). Art. 30's under-250-staff exemption does not apply when processing is "not occasional" ([GDPR Art. 30](https://gdpr-info.eu/art-30-gdpr/)), and systematic outreach arguably is. National email rules differ, with Germany reported to need prior consent even for B2B email, but that rests on vendor blogs, not statute ([Overloop](https://overloop.com/blog/b2b-cold-email-germany-gdpr-compliance)), so check it before encoding it as a hard block. HubSpot models two separate per-contact bases, one to process and one to communicate ([HubSpot one-to-one unsubscribe, search summary](https://knowledge.hubspot.com/one-to-one-email/manage-unsubscribe-links-for-one-to-one-emails)). The schema (inference) puts `lawful_basis`, `lia_id`, `country`, `objected_at` and `do_not_contact` on contacts. A `suppression_list` keyed by hashed email and hashed LinkedIn URL lets an objection survive erasure and block re-import from lemlist. An `erase_contact()` routine anonymises the contact, removes email bodies, writes the suppression hash, calls lemlist's cascading contact delete ([lemlist API index](https://developer.lemlist.com/llms.txt)) and logs to `privacy_requests`. A nightly retention job reduces non-converted prospects' email bodies to headers after a set period. Invoice data stays for the 7-year legal minimum, with that period stated in the privacy notice ([Ondernemersplein](https://ondernemersplein.overheid.nl/wetten-en-regels/facturen-maken-en-versturen/)).

```sql
create table contact_emails (
  id uuid primary key default gen_random_uuid(),
  contact_id uuid not null references contacts(id) on delete cascade,
  email text not null,
  is_primary boolean not null default false,
  bounced_at timestamptz
);
create unique index contact_emails_norm_uq on contact_emails (lower(trim(email)));
create unique index contact_emails_one_primary on contact_emails (contact_id) where is_primary;

create table organization_domains (
  organization_id uuid not null references organizations(id) on delete cascade,
  domain_normalised text not null unique,   -- registrable domain, no scheme/www/path
  is_primary boolean not null default false
);

create table contact_org_roles (
  contact_id uuid not null references contacts(id),
  organization_id uuid not null references organizations(id),
  relationship text not null,                -- owner, founder, employee, advisor, former_owner
  title text, is_primary boolean not null default false, is_current boolean not null default true,
  start_date date, end_date date, evidence_url text, verified_at timestamptz
);

create table stage_transitions (
  id bigserial primary key,
  object_type text not null, record_id uuid not null,
  from_stage_id uuid references pipeline_stages(id), to_stage_id uuid not null references pipeline_stages(id),
  amount numeric(14,2), close_date date,
  actor_type text not null, actor_id text, source text, changed_at timestamptz not null default now()
);

create table activity_links (
  activity_id uuid not null references activities(id) on delete cascade,
  contact_id uuid references contacts(id), organization_id uuid references organizations(id),
  lead_id uuid references leads(id), deal_id uuid references deals(id),
  project_id uuid references projects(id), ticket_id uuid references tickets(id),
  is_primary boolean not null default false,
  check (num_nonnulls(contact_id, organization_id, lead_id, deal_id, project_id, ticket_id) = 1)
);

create table external_ids (
  entity_type text not null, entity_id uuid not null,
  system text not null,                      -- lemlist_contact, lemlist_lead, gmail_thread, moneybird_invoice, kvk
  external_id text not null, external_url text, synced_at timestamptz,
  unique (system, external_id), unique (entity_type, entity_id, system)
);

create table sync_cursors (
  connector text not null, account text not null, stream text not null,
  cursor jsonb not null, last_success_at timestamptz, last_error text, backoff_until timestamptz,
  primary key (connector, account, stream)
);
```

Money is `numeric(14,2)` plus an ISO currency, never float, and VAT is stored per line because Article 226 requires the taxable amount per rate. Last activity, last contacted, last inbound, next activity, times contacted, weighted amount, time in stage and rotting are views or trigger-maintained columns, with their definitions written down, because HubSpot's own definitions differ by object and confuse users.

## Build the sales core first, money and service later

The phasing below is a recommendation (inference) ordered by what removes the most current pain. Phase 1 replaces the JSONL queue. The migration has its own rule: the old state files are a candidate list, so the import should take the latest row per leadId (the queue's own hygiene rule) and map the 106 status strings onto lead stage, `research_status` and `disqualify_reason`. It should resolve the 154 rows without a contactId through lemlist's search, then **backfill activities by pulling every contact's thread** rather than trusting the file's `openerSentAt` fields. ## Where the evidence is thin

Salesforce is the weakest leg. developer.salesforce.com returned 403 and help.salesforce.com rendered only a JavaScript shell, so every Salesforce field list here (Opportunity, Account, Contact, Lead, Case, Task, OpportunityContactRole, Quote, AccountTeamMember) is prior knowledge or a search summary. That rarely changes a recommendation, because the design copies HubSpot's shape and borrows only two Salesforce ideas: dated contact-to-account relations and history rows per stage change. Several HubSpot pages were reached only as search summaries: never-log, auto-association by domain, sensitive data, and the lead pipeline stage defaults (the Leads API itself was fetched). The national B2B email consent rules come from vendor blogs. Moneybird's create-invoice required fields and webhooks were cut off in the fetched page. Whether an Internal Google app using restricted Gmail scopes needs a CASA assessment is unresolved, because Google's own pages conflict. All default pipelines, probabilities, role definitions, widget lists, table designs and the phase plan are inferences fitted to Astra's documented process, not benchmarks anyone has measured. Finally, the queue counts were re-measured today and differ from the figures in the brief (3,181 rows rather than 3,095, and 107 distinct keys rather than about 40), because the file is still growing.

## Conclusion

The research changes the build question from "how much of HubSpot can Astra afford to rebuild" to "which three things does HubSpot get wrong for Astra". HubSpot's objects, fields, stage tables, task semantics and permission grid are close to right and cheap to copy. Its blind spots are exactly where Astra has been hurt. Activity sync is trusted rather than reconciled. There is no approval state between a draft and a send. Merges cannot be undone. Companies created through the API skip domain dedup. And there is one company per contact, with no history of who owned what. Each of these becomes a constraint in the schema (a unique index, a check, a state machine, an append-only log) rather than a rule in a markdown file, which is the real argument for building. Raka's CLAUDE.md currently asks a model to remember these rules every session, and a database would simply refuse to break them.

The second implication is about sequencing. The most valuable early asset is not the UI but `external_ids`, `sync_cursors`, `stage_transitions` and `audit_log`, because they turn every later report into a query over facts with provenance. If those four tables exist from day one, the dashboards, health scores, forecasts and client portal that come later can be built on history that is already trustworthy, instead of on a 106-value status column that only its author can read.
