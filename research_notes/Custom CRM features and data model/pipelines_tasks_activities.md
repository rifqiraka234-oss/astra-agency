# CRM pipelines, stages, lifecycle and status models, tasks, reminders and activity timelines (HubSpot first, Salesforce second, Pipedrive where useful)

Research date 2026-11-06. Benchmarks for a custom Postgres CRM for Astra Agency (LinkedIn via lemlist plus Gmail prospecting, then selling builds, running projects, managing accounts). Every finding below has an inline source. Items recalled from general product knowledge that I could not open a source for this session are put in Gaps, not Findings. Salesforce developer docs (developer.salesforce.com object reference and field reference) returned HTTP 403 to the fetcher, so Salesforce findings rely on search excerpts of those pages plus help.salesforce.com excerpts.

## 1. HubSpot pipelines and deal stages (multiple pipelines, probability, closed won/lost, conditional stage properties, stage restrictions, stage history)

### Takeaway
HubSpot models a pipeline as an ordered list of stages per object (deals, tickets, leads, custom objects), each stage carrying a probability (deals) or an Open/Closed flag (other objects), optional conditional "required properties" that pop up when a record enters the stage, and per-stage timestamps (Date entered / Date exited / time in stage). Pipeline rules can block skipping stages and moving backward, with closed stages exempt.

### Cited Findings
- Custom pipeline limits are shared across all objects and exclude each object's default pipeline. Seat-based portals: Free 0, Starter 15, Professional 100, Enterprise 350 (Flexible Seats & Credits portals: Starter 15, Professional 350, Enterprise 350). Lead pipelines require Professional or Enterprise; custom object pipelines require Enterprise. Editing pipelines/stages requires the "Edit property settings" permission. — [HubSpot KB, Set up and customize pipelines](https://knowledge.hubspot.com/object-settings/set-up-and-customize-pipelines)
- Default deal "Sales Pipeline" stages and probabilities: Appointment scheduled 20%, Qualified to buy 40%, Presentation scheduled 60%, Decision maker bought-in 80%, Contract sent 90%, Closed won 100% (Won), Closed lost 0% (Lost). Probability drives the weighted amount in board view. Custom probability values allowed. Both a Won and a Lost closed stage must exist for sales reports to work. — [HubSpot KB, Set up and customize pipelines](https://knowledge.hubspot.com/object-settings/set-up-and-customize-pipelines)
- For every object except deals, each stage is explicitly marked "Open" or "Closed" (deals derive closed-ness from Won/Lost probability). Default ticket "Support Pipeline" statuses: New, Waiting on contact, Waiting on us, Closed. — [HubSpot KB, Set up and customize pipelines](https://knowledge.hubspot.com/object-settings/set-up-and-customize-pipelines)
- Conditional stage properties: a rule in "Conditional logic rules" (operators "is equal to", "is any of", "is none of", "is known") shows dependent properties when a record is manually created in, or moved to, a stage; a "Required" checkbox blocks the create/update until the property has a value. Read-only (score/calculation) properties can't be stage properties. — [HubSpot KB, Set up and customize pipelines](https://knowledge.hubspot.com/object-settings/set-up-and-customize-pipelines)
- Pipeline rules (Super Admin, per pipeline): "restrict skipping stages" (all stages or selected) and "restrict moving backward" past selected stages. Exceptions: users can still skip directly to Closed won/Closed lost (for leads, Qualified/Unqualified), and can move backward out of a closed stage when reopening. Deal approval is a separate rule needing Sales Hub Enterprise. — [HubSpot KB, Set up pipeline rules](https://knowledge.hubspot.com/object-settings/set-up-pipeline-rules); [HubSpot KB, Set up rules for deal pipelines](https://knowledge.hubspot.com/crm-deals/set-up-rules-for-deal-pipelines)
- Conflict on enforcement scope: one version says rules are enforced on desktop, mobile, and via integrations/public APIs "when a user ID is being passed"; an older version says they don't apply to workflows/other APIs nor to Super Admins / users with Edit property settings permission. — [HubSpot KB, Set up pipeline rules](https://knowledge.hubspot.com/object-settings/set-up-pipeline-rules) (two page versions disagree)
- Deal stage history properties: "Date entered [stage ID]" (date/time the deal entered the stage), "Date exited [stage ID]", and "Time in current stage". — [HubSpot KB, Default deal properties](https://knowledge.hubspot.com/properties/hubspots-default-deal-properties)
- The same per-stage set exists for lifecycle stages: "Date entered [stage]", "Date exited [stage]", "Latest time in [stage]" (seconds since last entry, empty while currently in stage), "Cumulative time in [stage]" (seconds across all visits); latest/cumulative require Professional or Enterprise. — [HubSpot KB, Use lifecycle stages](https://knowledge.hubspot.com/records/use-lifecycle-stages)
- Closed/forecast fields on deals: "Closed lost reason", "Closed won reason", "Forecast category" with values Not forecasted, Pipeline, Best case, Commit, Closed won; "Forecast probability" (custom percent, rep override) separate from "Deal probability" (stage-driven); "Weighted amount" = Amount x Deal probability; "Is closed won" / "Is closed lost" booleans; "Close date" (expected or actual); "Days to close" (Create date to Close date); "Next step" free text; "Priority"; "Deal type" defaults New Business / Existing Business (editable). — [HubSpot KB, Default deal properties](https://knowledge.hubspot.com/properties/hubspots-default-deal-properties)
- Activity counters on deals: "Number of times contacted" (associated activities, excludes tasks and notes) vs "Number of sales activities" (includes tasks and notes). — [HubSpot KB, Default deal properties](https://knowledge.hubspot.com/properties/hubspots-default-deal-properties)

### Inferences
- Postgres shape that mirrors this: `pipelines(id, object_type, name, position, is_default)`, `pipeline_stages(id, pipeline_id, name, position, probability numeric NULL, state enum('open','won','lost') , is_closed bool, rot_days int NULL)`, `stage_required_fields(stage_id, field_key, condition jsonb NULL)`, and an append-only `stage_transitions(record_type, record_id, from_stage_id, to_stage_id, changed_by, changed_at, source)` from which Date entered / Date exited / time-in-stage / cumulative time are computed (views or triggers), instead of HubSpot's one-column-per-stage approach. This also covers Salesforce OpportunityHistory (section 3) in one table.
- For a handful of users, enforce "no skip / no backward" in application code with a `force` override for admins, and always allow jump-to-closed and reopen-from-closed, matching HubSpot's exceptions.
- Keep both a stage-driven probability and an optional rep override (`forecast_probability`) plus a `forecast_category` enum; cheap to add, useful for a one-person forecast.
- Make `lost_reason` a required stage field on the Lost stage (picklist + free text), which HubSpot achieves via conditional required properties.

### Gaps
- Exact HubSpot "Deal stage history" UI (the stage history card) and whether HubSpot logs who moved the stage were not opened this session; property history per field exists in HubSpot generally but was not verified here.
- Which ticket statuses default to Open vs Closed was not stated on the page.

## 2. HubSpot lifecycle stages, Lead Status, and the Leads object with its lead pipeline

### Takeaway
HubSpot runs three overlapping status systems: the contact/company Lifecycle stage (funnel position, auto-moves forward only), Lead Status (sub-states of SQL, a free picklist), and the newer Leads object (a separate record per prospecting attempt with its own pipeline New, Attempting, Connected, Qualified, Disqualified, moved automatically by logged outreach). For a custom CRM, the Leads-object pattern is the closest fit to lemlist/Gmail prospecting.

### Cited Findings
- Default lifecycle stages in order: Subscriber, Lead, Marketing Qualified Lead, Sales Qualified Lead, Opportunity ("associated with a deal"), Customer ("has at least one closed deal"), Evangelist, plus Other. Stages are customizable and custom stages can be created. — [HubSpot KB, Use lifecycle stages](https://knowledge.hubspot.com/records/use-lifecycle-stages)
- Default automatic updates "will only move the stage forward". Automation settings include a default stage for new records, updates based on associations, and a default stage per connected app. Moving backward is manual (record, bulk, import, workflow); automation must first clear the value. Moving backward clears the legacy "Became a [stage] date" for the higher stage; calculated date/time properties are not cleared. — [HubSpot KB, Use lifecycle stages](https://knowledge.hubspot.com/records/use-lifecycle-stages)
- Lead Status describes sub-stages within Sales Qualified Lead. Default values: New, Open, In Progress, Open Deal, Unqualified, Attempted to Contact, Connected, Bad Timing. Customizable. — [HubSpot KB, Use lifecycle stages](https://knowledge.hubspot.com/records/use-lifecycle-stages)
- Leads object: default lead pipeline stages New, Attempting, Connected, Qualified, Disqualified; leads in a custom pipeline aren't eligible for default lead stage automation. — [HubSpot KB, Set up and customize pipelines](https://knowledge.hubspot.com/object-settings/set-up-and-customize-pipelines)
- Lead automation (Sales Hub Professional/Enterprise, default pipeline only): New to Attempting when a user sends/logs an email or call, or logs an SMS, LinkedIn or WhatsApp message. Attempting to Connected when the lead replies to an email, a meeting is booked with outcome Completed, or a call is logged with outcome Connected. Manually moving a lead backward stops future automatic updates for that lead. — [HubSpot KB, Set up lead pipeline automation](https://knowledge.hubspot.com/object-settings/set-up-lead-pipeline-automation)
- Leads can be auto-created when a contact enters a chosen lifecycle stage (not when the change came from company lifecycle sync), and a follow-up lead of a chosen lead type can be auto-created when a selected disqualification reason is applied. Custom workflow actions can run on entry to a lead stage. — [HubSpot KB, Set up lead pipeline automation](https://knowledge.hubspot.com/object-settings/set-up-lead-pipeline-automation)
- Task defaults include a checkbox to be reminded to create a follow-up task when disqualifying a lead. — [HubSpot KB, Create tasks](https://knowledge.hubspot.com/tasks/create-tasks)
- Third-party descriptions (secondary): Qualified and Disqualified are manual judgment stages; admins edit stages at Settings > Leads > Pipeline. — [Six & Flow](https://www.sixandflow.com/marketing-blog/setting-up-the-lead-object); [Hublead](https://hublead.io/blog/hubspot-leads-object)

### Inferences
- Astra's lemlist states map almost one to one onto the HubSpot lead pipeline: New (imported, invite queued), Attempting (invite sent / opener sent), Connected (accepted and replied, or meeting completed), Qualified (converted to a deal), Disqualified (with reason, e.g. NO_STRONG_ANGLE, DO_NOT_CONTACT, BLOCKED_NEEDS_INFO, former owner, wrong company). The repo's existing queue statuses (UNRESEARCHED, DRAFTED, SENT, NO_STRONG_ANGLE, BLOCKED_NEEDS_INFO, DO_NOT_CONTACT) are research sub-states and would sit as a separate `research_status` field rather than pipeline stages.
- LinkedIn has a distinct step HubSpot does not model: invite sent vs invite accepted. A custom CRM should either add an "Accepted" stage between Attempting and Connected, or record acceptance as a dated event (`linkedin_accepted_at`) so the "Silent accepted" bucket (accepted, no real message) is a query, not a stage.
- Keep lifecycle stage on contact/company as a derived, forward-only field (Lead, Opportunity when an open deal exists, Customer when a won deal exists, Former customer/Churned optional), computed from leads/deals rather than edited by hand; store a separate manual override only if needed.
- Mirror "manual backward move disables auto-progression" with a boolean `auto_progress_enabled` on the lead row.

### Gaps
- Official HubSpot docs on the lead object's own properties (lead name, lead type, lead label hot/warm/cold) and whether qualifying a lead auto-creates a deal were not found on the pages opened.
- Exact HubSpot rules for "deal created sets contact to Opportunity" and "closed won sets Customer" are in a separate KB article not opened; only the stage definitions above are sourced.

## 3. Salesforce: Lead Status, lead conversion, Opportunity stages/probability/forecast category, sales processes, OpportunityHistory, Path

### Takeaway
Salesforce keeps Leads as a separate object that is "converted" into Account + Contact (+ optional Opportunity) using a Lead Status value flagged Converted; Opportunity StageName maps to a default probability and a forecast category, and every stage/amount/close date change writes an OpportunityHistory row.

### Cited Findings
- Lead conversion requires a Lead Status picklist value flagged "Converted"; common labels are "Closed - Converted" and "Closed - Not Converted". — [MarCloud, Salesforce Lead Status](https://marcloudconsulting.com/sf-basics/salesforce-lead-status/)
- Conversion creates the account, contact and optionally an opportunity; it does not overwrite existing account/contact data with lead data; with record types, the new owner's default record type is applied; universally required fields and validation rules are enforced during conversion when "Require Validation for Converted Leads" is set. — [Salesforce Help, Considerations for Converting Leads](https://help.salesforce.com/s/articleView?language=en_US&id=sales.leads_notes.htm&type=5); [Salesforce Help, Lead Conversion Field Mapping](https://help.salesforce.com/s/articleView?language=en_US&id=sf.lead_conversion_mapping.htm&type=5)
- Path: each stage can show up to five key fields specific to that path, displayed beneath the path at that stage (plus "guidance for success" text). — [SalesforceBen, Lead conversion](https://www.salesforceben.com/salesforce-lead-conversion/) (search excerpt)
- OpportunityHistory stores the stage history of an opportunity; each row stores values after the change: StageName, Probability, Amount, CloseDate, ExpectedRevenue, ForecastCategory ("To Forecast Category"). — [Salesforce field reference, OpportunityHistory](https://developer.salesforce.com/docs/platform/field-reference/references/field-reference/salesforce-field-reference-opportunityhistory.html); [CData, OpportunityHistory](https://cdn.cdata.com/help/RFJ/rcmd/pg_table-opportunityhistory.htm)
- Opportunity exposes ForecastCategoryName; stage drives forecast category through admin-editable mappings (example: Negotiation/Review, 90%, Commit). — [Salesforce field reference, Opportunity](https://developer.salesforce.com/docs/platform/field-reference/references/field-reference/salesforce-field-reference-opportunity.html); [Salesforce Help, Stage to Forecast Category mappings](https://help.salesforce.com/s/articleView?id=sales.faq_forecasts_category_mapping.htm&language=en_US&type=5)
- Salesforce Task: WhoId (Contact or Lead), WhatId (related record such as Opportunity, Account or custom object), ActivityDate is a due DATE with no time component, ReminderDateTime when a reminder fires, IsRecurrence ("Create Recurring Series of Tasks"), TaskSubtype picklist. — [Salesforce field reference, Task](https://developer.salesforce.com/docs/platform/field-reference/references/field-reference/salesforce-field-reference-task.html) (search excerpt; page 403 to direct fetch); [CData, Task](https://cdn.cdata.com/help/RFK/mcp/pg_table-task.htm)

### Inferences
- The polymorphic Who/What split is the useful idea: one "person" link (contact or lead) plus one "thing" link (company, deal, project). In Postgres prefer a join table `activity_links(activity_id, entity_type, entity_id, is_primary)` over polymorphic FKs, which also gives HubSpot-style many-to-many associations.
- Avoid a separate Lead table that is "converted" and frozen (Salesforce) if contacts already exist from lemlist; HubSpot's approach (a lead is a pipeline record attached to an existing contact/company) avoids data duplication. Conversion then = create deal from lead, set lead stage Qualified, copy chosen past activities.
- An OpportunityHistory-style table is the same as the `stage_transitions` table in section 1, extended with amount/close_date/probability snapshots so pipeline-at-date-X reporting is possible.

### Gaps
- Not verified this session (developer.salesforce.com returned 403): the standard Opportunity stage picklist with default probabilities (Prospecting 10% ... Closed Won 100%), the standard forecast category list (Omitted, Pipeline, Best Case, Commit, Closed), Sales Process + record type mechanics, Task Status/Priority defaults, RecurrenceType/RecurrenceInterval/RecurrenceRegeneratedType field details, Event fields (StartDateTime, EndDateTime, IsAllDayEvent, Location, ShowAs), and Shared Activities (TaskRelation/EventRelation, up to 50 contacts). These are commonly known but need a reopen of the Salesforce object reference before being cited.

## 4. Pipedrive: rotting / idle days, activity-based selling, next activity on every deal

### Takeaway
Pipedrive sets a per-stage "Rotting in (days)" threshold based on the deal's last update, paints rotten deals red, and flags any deal with no scheduled activity with a warning icon, making "every open deal has a next activity" the core discipline.

### Cited Findings
- Rotting is configured per stage in the pipeline editor ("Rotting in (days)" toggle plus number of inactive days). The clock is based on the deal's last updated time; it is reset by marking activities done, adding notes/files, email actions (send, receive, unlink, delete, archive) and some updates not visible in the changelog. Rotten deals show a red tile. Restore by scheduling an activity or editing any deal detail. The feature ignores the next activity date, so a deal with a far-future activity can still rot. — [Pipedrive KB, The Rotting feature](https://support.pipedrive.com/en/article/the-rotting-feature)
- Pipedrive warns that long rotting windows (e.g. 20 days) to accommodate far-future activities can hurt short-term productivity. — [Pipedrive KB, The Rotting feature](https://support.pipedrive.com/hc/en-us/articles/206760949-The-Rotting-Feature) (search excerpt)
- Rotting cannot trigger automations directly (not a user action); suggested workaround is a stage-change triggered automation with a delay. — [Pipedrive Community](https://community.pipedrive.com/discussion/9238/is-there-a-way-to-automatically-move-deals-without-activity-for-some-time)
- Deals with no linked/scheduled activity show a yellow caution icon in pipeline view, by design, because Pipedrive is built around activities moving deals forward; users report Pipedrive prompting for a next activity after completing one, even on lost deals. — [Pipedrive Community, caution symbol](https://community.pipedrive.com/discussion/14827/deal-view-show-label-text-and-hide-yellow-caution-symbol); [Pipedrive Community, Next activity for lost deals](https://community.pipedrive.com/discussion/comment/17159)
- Users can filter deals with no next activity or an overdue activity, but say higher-level reporting on it is hard natively. — [Pipedrive Community, Reporting on deal activities](https://community.pipedrive.com/discussion/9316/reporting-on-deal-activities)

### Inferences
- For Astra: store `rot_days` per stage; compute `last_touched_at` on deals (and leads) from activities and field edits; a deal is "rotting" when `now() - last_touched_at > rot_days`. Also compute `next_activity_at` (min due of open tasks/future meetings) and flag open records where it is NULL or past. Both are cheap views.
- Copy the "complete a task, get prompted for the next one" UX, but suppress it on closed deals/leads (the complaint above).
- Because lemlist sequences send automatically, define "touch" as human or sequence outbound plus any inbound reply, and keep separate `last_outbound_at` and `last_inbound_at` so a sequence auto-send does not hide a deal that nobody has actually worked.

### Gaps
- Official Pipedrive documentation on activity types, the "next activity" field definition, and the "activity-based selling" methodology page were not opened; findings on the caution icon come from community posts.

## 5. Tasks and reminders (HubSpot task fields, queues, recurrence, overdue; Salesforce Task)

### Takeaway
A HubSpot task is an engagement with title, type (To-do, Call, Email, plus LinkedIn Sales Navigator InMail/Connection request), priority (Low/Medium/High), due date-time, a single email reminder time, owner, optional queue, notes, a status (Not started/Completed), many-to-many associations, and optional "repeat every N days/weeks/months/years" which spawns the next task when the prior one is completed, deleted or goes overdue.

### Cited Findings
- UI task fields: Title (including "call" or "email" in the title auto-sets the type); Type: Call, Email, To-do, plus "Sales Navigator - Send InMail" and "Sales Navigator - Connection request" with the LinkedIn Sales Navigator integration; Priority: Low, Medium, High; Associations to any records (contacts, companies, deals...), unassociated tasks are allowed but don't show on timelines; Assigned to a user (or "Customer" to assign to a contact); Queue (existing or new); Due date with time; Reminder (email reminder to owner); Notes. — [HubSpot KB, Create tasks](https://knowledge.hubspot.com/tasks/create-tasks)
- Recurring tasks: "Set to repeat", every N days, weeks, months or years; the repeat keeps title, assignee, notes and associations; a new task is created when the previous is completed, deleted or becomes overdue; requires a Core, Sales or Service seat. — [HubSpot KB, Create tasks](https://knowledge.hubspot.com/tasks/create-tasks)
- User defaults: default due date (N days/weeks after creation), default due time, default reminder ("No reminder" option), and checkboxes to be prompted for a follow-up task when completing a task from a list view or disqualifying a lead. Creation paths: tasks index, bulk from object index (one identical task per selected record), record sidebar, "Create a To-do" checkbox after logging an activity, Gmail Chrome extension, workflows (Professional/Enterprise), and sequence task steps. — [HubSpot KB, Create tasks](https://knowledge.hubspot.com/tasks/create-tasks)
- API properties: `hs_timestamp` (required, due date), `hs_task_subject` (title), `hs_task_body` (notes), `hs_task_status` (`NOT_STARTED` or `COMPLETED`; an example payload on the same page uses `WAITING`, a doc inconsistency), `hs_task_priority` (`LOW`/`MEDIUM`/`HIGH`), `hs_task_type` (`EMAIL`/`CALL`/`TODO`), `hs_task_reminders` (epoch ms), `hubspot_owner_id`. Associations by association type id (e.g. task_to_contact). Pin one activity per record via `hs_pinned_engagement_id`. Deleted tasks go to a recycle bin and can be restored. — [HubSpot Developers, Tasks API guide](https://developers.hubspot.com/docs/api-reference/crm-tasks-v3/guide)
- Third-party mirror of HubSpot docs: task queues let a rep work tasks back to back; the official page confirms adding a task to a queue. — [HubSpot KB, Create tasks](https://knowledge.hubspot.com/tasks/create-tasks); [Vested Marketing mirror](https://knowledge.vested.marketing/knowledge/how-to-create-tasks)
- Salesforce Task stores due date as a DATE (no time) in ActivityDate and a separate ReminderDateTime; recurrence is flagged by IsRecurrence. — [Salesforce field reference, Task](https://developer.salesforce.com/docs/platform/field-reference/references/field-reference/salesforce-field-reference-task.html) (search excerpt)

### Inferences
- Task table for Astra: `tasks(id, title, body, type enum('todo','call','email','linkedin_connect','linkedin_message','linkedin_nudge','meeting_prep','send_artifact','renewal','checkin'), priority enum('low','medium','high'), status enum('not_started','in_progress','waiting','completed','cancelled'), due_at timestamptz, due_date_only bool, remind_at timestamptz[] , owner_id, queue_id NULL, recurrence_rule text NULL (RRULE), recurrence_parent_id NULL, completed_at, completed_by, created_from enum('manual','sequence','workflow','stage_entry','recurrence','ai'), created_at)`, plus `task_links(task_id, entity_type, entity_id, is_primary)`.
- Record `completed_at` explicitly; HubSpot's API guide documents none and completion only via status, which makes "completed late" reporting harder.
- Implement HubSpot's recurrence semantics (next instance spawned on complete/delete/overdue) rather than pre-materialising a series; it is simpler and avoids orphan future rows. Store RRULE so "every 3 months on the first Monday" QBRs are expressible.
- Overdue = `status not in (completed,cancelled) and due_at < now()`; "Due today" and "Overdue" are saved views, not stored fields. Reminders: a `reminders` job table polled by a worker that emails/pushes and marks `sent_at`.
- Add the "Draft before send" approval as a task type or status ("awaiting_approval") since every outbound message in this repo needs Raka's explicit go.

### Gaps
- Full list of HubSpot reminder offsets, due date presets, and the "Complete tasks" / overdue behaviour article were not opened. HubSpot's newer native LinkedIn task types beyond Sales Navigator were not confirmed.

## 6. Activities / engagements and the activity timeline (types, fields, roll-up to associated records, computed last/next activity dates)

### Takeaway
HubSpot stores each activity (email, call, meeting, note, task, communication for LinkedIn/SMS/WhatsApp, postal mail) as an engagement object associated many-to-many with contacts, companies, deals and tickets; the timeline of a record is simply all engagements associated to it, and auto-association rules copy contact-logged activity onto the primary company and up to five most recent open deals. "Last activity date", "Last contacted" and "Next activity date" are computed roll-ups with different inclusion rules.

### Cited Findings
- Communications engagement: logs WhatsApp, LinkedIn and SMS messages to record timelines; channel set by `hs_communication_channel_type` with documented values `WHATS_APP`, `LINKEDIN_MESSAGE`, `SMS`; endpoint `/crm/v3/objects/communications`, newer date-versioned `/crm/objects/2026-03/communications`; not for marketing SMS. A third-party connector uses `WHATSAPP`/`LINKEDIN` instead, an unresolved discrepancy. — [HubSpot Developers, Communications API (latest)](https://developers.hubspot.com/docs/api-reference/latest/crm/objects/communications/guide); [HubSpot Developers, Communications API 2026-03](https://developers.hubspot.com/docs/api-reference/2026-03/crm/objects/communications/guide.md)
- Auto-association rules (default): only one-to-one emails, meetings, notes and calls auto-associate, and the records must already be associated before logging. Logged on a contact: goes to the contact's primary company and its five most recent open deals. Logged on a company: to its five most recent open deals (emails/outbound calls also to the contacts emailed/called). Logged on a deal: to the deal's primary company and five most recent open deals. When a contact moves to a new company, past activities stay with the old company. Super Admins can customise (e.g. meetings to only the most recent deal). When creating a deal or ticket you can copy the associated record's past calls, emails, notes, meetings and tasks for a chosen time frame, up to 2,000 per record. — [HubSpot KB, Associate activities with records](https://knowledge.hubspot.com/records/associate-activities-with-records)
- Exceptions: tasks created from the Gmail Chrome extension are not associated with company or deals; tasks created from sequences on contacts are not associated with any records; emails sent from the mobile app or conversations inbox go only to the contacts emailed. — [HubSpot KB, Associate activities with records](https://knowledge.hubspot.com/records/associate-activities-with-records)
- Contact "Last contacted": last chat, call, non-forwarded one-to-one email, meeting, or manually entered LinkedIn/SMS/WhatsApp message. "Last activity date": most recent past note, call, tracked/logged sales email, meeting, LinkedIn/SMS/WhatsApp message or chat, and also completed tasks. "Next activity date": date of the next upcoming activity. — [HubSpot KB, Default contact properties](https://knowledge.hubspot.com/properties/hubspots-default-contact-properties)
- Deal equivalents: "Last activity date" (past logged activity incl. completed tasks), "Next activity date" (next upcoming activity for a deal), "Last contacted" (chat, call, non-forwarded one-to-one email, meeting or message logged for the deal). — [HubSpot KB, Default deal properties](https://knowledge.hubspot.com/properties/hubspots-default-deal-properties)
- Company "Last activity date" is described in the community as covering notes, calls, sales emails, meetings, tasks or chats logged on the company record (unofficial wording). — [HubSpot Community](https://community.hubspot.com/t5/Tips-Tricks-Best-Practices/Key-Account-Management-Workflow/td-p/769249)
- Lead stage automation counts logged LinkedIn, SMS and WhatsApp messages as outreach (New to Attempting). — [HubSpot KB, Set up lead pipeline automation](https://knowledge.hubspot.com/object-settings/set-up-lead-pipeline-automation)

### Inferences
- One `activities` table with a `kind` enum ('email','linkedin_message','linkedin_invite','linkedin_accept','call','meeting','note','task','stage_change','artifact_sent','system') and `direction` ('outbound','inbound','internal'), `occurred_at`, `actor` (user, lemlist sequence, contact), `channel_ref` (Gmail message/thread id, lemlist activity id, contactId) with a UNIQUE constraint on (source, external_id) for idempotent sync, `body`, `meta jsonb`. Links via `activity_links` (many-to-many, `is_primary`). Timeline of a company = activities linked to the company UNION activities linked to its contacts (decide: copy links at write time HubSpot-style, or resolve at read time; read-time join avoids HubSpot's "old company keeps history" quirk only if you store contact-company membership with valid_from/valid_to).
- Given the repo's history of lemlist preview/bulk endpoints under-reporting, the CRM should ingest per-thread (`get_inbox_conversation`) and reconcile message counts against `totalItems`, storing every message as its own activity row so the "whole thread" rule is a single query.
- Computed fields as SQL views (or materialised columns refreshed by trigger): `last_contacted_at` (outbound human/sequence message, call, meeting), `last_inbound_at` (their reply), `last_activity_at` (any incl. completed tasks and notes), `next_activity_at` (earliest open task due or future meeting), `times_contacted`. Keep the definitions written down because HubSpot's own definitions differ by object and that difference confuses users.
- Distinguish "last contacted" from "last replied": for Astra, "is it our turn" (last message is theirs with real content) is the key triage field and should be a stored/computed boolean per thread.

### Gaps
- HubSpot postal mail engagement fields and the email engagement property list (hs_email_direction, status) were not opened. Official company-level definitions of Last contacted / Next activity date were not found.

## 7. Meetings: outcome, type, booking links, account-management check-ins and QBR reminders; agency cadences and renewals

### Takeaway
HubSpot meetings carry an outcome (Scheduled, Completed, Rescheduled, No show, Canceled; calendar-synced meetings start as Scheduled) and a configurable "call and meeting type" picklist; outcome Completed is what moves a lead to Connected. Recurring account check-ins are best modelled as recurring tasks/meetings; I found no vendor-documented agency cadence standard.

### Cited Findings
- `hs_meeting_outcome` values: scheduled, completed, rescheduled, no show, canceled (API returns values only for these system defaults; custom outcomes come from a separate enum). Calendar-synced meetings default to Scheduled; manually logged meetings can have an outcome set. Legacy 0/1 count fields exist per outcome (completed, no show, rescheduled, canceled). — [HubSpot KB, Default activity properties](https://knowledge.hubspot.com/properties/hubspots-default-activity-properties); [HubSpot Developers, Meetings guide (2026-03)](https://developers.hubspot.com/docs/api-reference/2026-03/crm/activities/meetings/guide.md)
- Changing meeting outcome or meeting type does not send an update to attendees; some users add custom "call and meeting types" like "meeting attended"/"meeting no show" as a workaround. — [HubSpot Community, Meeting Outcome](https://community.hubspot.com/t/meeting-outcome/1675)
- A meeting booked and set to Completed moves a lead from Attempting to Connected. — [HubSpot KB, Set up lead pipeline automation](https://knowledge.hubspot.com/object-settings/set-up-lead-pipeline-automation)
- Recurring tasks (every N days/weeks/months/years) are HubSpot's native mechanism for repeating reminders such as periodic check-ins. — [HubSpot KB, Create tasks](https://knowledge.hubspot.com/tasks/create-tasks)

### Inferences
- Meeting table fields for Astra: `title, start_at, end_at, timezone, location/video_url, calendar_event_id (Google Calendar), booking_source ('booking_link','manual','calendar_sync'), meeting_type enum ('discovery','prototype_review','proposal','kickoff','project_checkin','qbr','renewal'), outcome enum (as HubSpot), brief_path, notes, attendees (contact links)`. Outcome Completed should auto-advance the linked lead and drive the existing "meeting brief" workflow in CLAUDE.md (brief emailed and saved to `logs/meetings/`).
- Account management for a small agency: model an `accounts`/customer status on the company (Active project, Retainer, Maintenance, Dormant, Churned) and attach recurring tasks: project check-in (e.g. every 2 weeks during a build), post-launch review (one-off, ~30 days after go-live), QBR (every 3 months for retainers), renewal reminder (N days before `contract_end_date` / domain or hosting renewal). These are design suggestions, not sourced benchmarks.
- A second deal pipeline for existing customers ("Existing Business" deal type in HubSpot) separates upsells/renewals from new builds; a third pipeline (or a `projects` table with its own stages: Kickoff, Design, Build, QA, Launched, Support) covers delivery after Closed won.

### Gaps
- Official HubSpot documentation of the meeting type property and of the Meetings scheduling (booking link) tool fields was not opened. No authoritative source was found this session for agency-specific account management cadences or renewal reminder best practices; recommendations above are inference.
- Attio (lists, status attributes, record timelines) was not researched within the call budget.
