## 1. HubSpot workflows: triggers, actions, re-enrollment, goals/unenrollment, logs, errors, sequences, common sales automations

### Takeaway
HubSpot workflows are object-scoped (contact, company, deal, ticket, custom object, and so on). Five trigger families are worth copying: filter-based, event-based, schedule/date-based, webhook and manual. Actions fall into delays, branches, CRM record actions, notifications, and data-ops actions (custom code, webhook). Re-enrollment is off by default. Unenrollment is driven by "no longer meets criteria", goal and suppression settings. Action logs are kept for 90 days with automatic retry on transient errors. A small agency needs about 15 of these primitives, not HubSpot's 80+.

### Cited Findings

**Enrollment triggers**
- There are five trigger types. Event-based fires "when an event occurs", such as a form submission or custom event. Filter-based fires "when filter criteria is met", when property values match. Webhook-based fires "when a webhook is received" and is Data Hub Pro/Enterprise only. Schedule-based fires on a calendar date or a date property, and needs extra filter criteria to enroll automatically. Manual covers by-hand, bulk from segments/lists, from other workflows or bots, and the "Enroll in another workflow" action. — [HubSpot KB, enrollment triggers](https://knowledge.hubspot.com/workflows/set-your-workflow-enrollment-triggers)
- Filter triggers can express "has not" conditions, such as an event that didn't happen, and can use associated (cross-object) data. Event triggers can't detect non-occurrence, because "it is not possible to determine if an event did not occur". Associated-object data is reached through the data panel instead. — [HubSpot KB, enrollment triggers](https://knowledge.hubspot.com/workflows/set-your-workflow-enrollment-triggers)
- Limits: up to 250 filters in a workflow's enrollment triggers, and only one "refine by" criterion per event trigger. Some triggers only show if the user has the matching permission, such as Forms. Creating or editing workflows needs Super Admin or the Workflows permission. Workflows are Professional/Enterprise in Marketing, Sales, Service, Data, Smart CRM and Revenue hubs. — [HubSpot KB, enrollment triggers](https://knowledge.hubspot.com/workflows/set-your-workflow-enrollment-triggers)

**Re-enrollment**
- By default a record enrolls only the first time it meets the triggers. Filter triggers re-enroll only if re-enrollment criteria are configured. Event triggers let you choose "only once or each time the event occurs". — [HubSpot KB, enrollment triggers](https://knowledge.hubspot.com/workflows/set-your-workflow-enrollment-triggers)

**Actions (current catalogue)**
- *Delays*: until a calendar date, until a date property, until an event occurs, a set amount of time (days/hours/minutes), until a day of the week, or until a time of day. — [HubSpot KB, workflow actions](https://knowledge.hubspot.com/workflows/choose-your-workflow-actions)
- *Branches*: on one property or a prior action's output (value-equals, no AND/OR, up to 250 branches per property), on AND/OR filter logic, or random percentage split (Marketing Pro/Ent). — [HubSpot KB, workflow actions](https://knowledge.hubspot.com/workflows/choose-your-workflow-actions)
- *Flow control*: "Go to workflow" enrolls the record in another same-object workflow while it stays in the original. It skips that workflow's triggers and is blocked by suppression or active enrollment. "Go to action" jumps to an earlier-built action, only inside if/then branches, and is designed to prevent loops. — [HubSpot KB, workflow actions](https://knowledge.hubspot.com/workflows/choose-your-workflow-actions)
- *CRM actions*: Edit record (set, copy or clear property values, including on associated records), Create record (contact, company, deal, ticket, lead, custom object), Create task, Create note (with tokens), Increase/decrease number property, Create associations, apply/update/remove association labels, Rotate record to owner (Sales/Service Pro/Ent, paid activated users only), Delete contact (restorable for 90 days), Convert deal to invoice, Create quote, Add line item to deal. — [HubSpot KB, workflow actions](https://knowledge.hubspot.com/workflows/choose-your-workflow-actions)
- *Communication*: Send in-app notification and Send internal email notification to users, teams or owners (all workflow types), Send marketing email (Marketing/Service Pro+), Enroll/unenroll in sequence (Sales Hub, sender needs a paid seat), SMS, WhatsApp, Slack notification, Create Slack channel on a deal/company, and Google Chat. — [HubSpot KB, workflow actions](https://knowledge.hubspot.com/workflows/choose-your-workflow-actions)
- *Data ops*: Custom code (JavaScript), Format data, and Send a webhook. All three are **Data Hub Professional/Enterprise only**. — [HubSpot KB, workflow actions](https://knowledge.hubspot.com/workflows/choose-your-workflow-actions)
- *AI actions* (2025-26): Data Agent custom prompt, research, fill smart property, summarize record, run agent, and use a custom LLM. Most are beta and all use HubSpot Credits. — [HubSpot KB, workflow actions](https://knowledge.hubspot.com/workflows/choose-your-workflow-actions)

**Unenrollment and goals**
- In contact-based workflows you can unenroll records that no longer meet the enrollment criteria, meet the workflow goal, or are added to a suppression segment. "No longer meets enrollment criteria" is off by default. — [HubSpot KB FAQ / unenrollment (via search summary)](https://knowledge.hubspot.com/workflows/workflows-faq); [HubSpot KB, unenrollment in company/deal/ticket workflows](https://knowledge.hubspot.com/articles/kcs_article/workflows/set-unenrollment-triggers-in-company-deal-ticket-quote-based-workflows)
- One community user found that a goal kept records from re-enrolling, and deleting the goal fixed it. This is anecdotal. — [search summary of HubSpot community](https://knowledge.hubspot.com/workflows/workflows-faq)

**Logs and errors**
- Action logs sit under Workflow > View details > Action logs. "All workflow action log data is stored for 90 days." Once a daily limit is exceeded, success/info logs stop being stored for that day but error logs continue. Logs export to CSV. — [HubSpot KB, workflow alerts/errors (search summary)](https://knowledge.hubspot.com/workflows/understand-workflow-alerts-errors?app=1)
- Transient errors (rate limiting, webhook timeouts, simultaneous rotate actions) "will retry automatically at a later time". When several records rotate at once, only one goes through and the others retry. A slow webhook server can get the action executed while HubSpot logs it as failed and retries, which "can lead to duplicate effects". Non-transient errors need "Edit automation" or "Ignore". — [HubSpot KB, troubleshoot common workflow errors](https://knowledge.hubspot.com/workflows/troubleshoot-common-workflow-errors?no_head=1)

**Deal rotting (Pipedrive as the reference)**
- Pipedrive sets rotting per pipeline stage with a "Rotting in (days)" toggle. The timer runs from the deal's last update time. Marking activities done and sending/receiving/deleting linked emails reset it, and some of those resets don't show in the changelog. Rotting ignores the next activity date. Users can't choose which updates reset the timer, and Pipedrive suggests an automation that notifies when a deal stays in a stage too long. — [Pipedrive KB, The Rotting feature](https://support.pipedrive.com/en/article/the-rotting-feature); [Pipedrive community thread](https://community.pipedrive.com/discussion/17420/rotting-days-resetting-with-field-updates-or-client-communication)

### Inferences
- **Minimum viable trigger set for the custom CRM**: (a) record created, (b) property changed, from/to a value or just changed, (c) record matches filter (evaluated on change, plus a "has not" variant run by a periodic sweep), (d) date-relative (N days before/after a date field, such as close_date or invoice_due), (e) schedule/cron, (f) inbound webhook, (g) manual "run on these records". That covers HubSpot's five families plus Twenty's created/updated/deleted. Event-based enrollment can't express "didn't happen", so non-occurrence rules like "no activity in 14 days" have to be sweeps over filter state, not event listeners. This is how rotting works too.
- **Minimum viable action set**: set/copy/clear field (own or associated record), create record, create task (assignee, due offset, linked record), create note, add association, internal notification (in-app + email + Slack), send email from template to a contact (only through the mailbox integration), rotate owner (round robin; Twenty also offers random and load-balanced), delay (for duration, until date field, until weekday/time), if/then branch (value-equals and AND/OR), go-to-workflow, outbound webhook/HTTP, and custom code as a later phase. HubSpot charges Data Hub Pro for webhooks and custom code. In-house they're cheap and give the most leverage.
- **Re-enrollment semantics to copy exactly**: default once per record per workflow, an explicit "allow re-enrollment when X changes again", and event triggers with "once" or "every time". Store an `enrollment` row per (workflow_version, record), unique unless re-enrollment is allowed, to enforce this.
- **Rotting is better implemented as a derived field** (`stage_entered_at`, `last_activity_at`, a per-stage `rot_after_days`) than as a workflow, with an optional workflow on "deal became rotten". Let the agency choose which activity types reset the timer, which is the thing Pipedrive users complain they can't do.
- Standard agency sales automations to ship as templates (HubSpot-style patterns, from the action catalogue above): deal enters "Proposal sent" → create follow-up task due +3 days for the owner; deal enters "Won" → notify owner and team, create project/onboarding record, set close date to today if empty, create invoice draft; deal created without owner → rotate owner; no activity for X days on an open deal → notify owner (rotting); close date passed while still open → task "update close date or mark lost"; invoice overdue → task for the account manager.
- **Sequences vs workflows** (inference from HubSpot's action catalogue, where "Enroll in sequence" is a workflow action needing a paid Sales seat): sequences are per-rep, 1:1 email and task cadences sent from the rep's own mailbox that stop on reply. Workflows are record-level system automation. For a few-user agency, sequences are optional, and a "follow-up cadence" template of workflow tasks may be enough.

- No official HubSpot page was read on sequences vs workflows (unenroll-on-reply, sending limits). The sequences description above is inference.
- HubSpot "workflow revision history / versioning" wasn't verified this session.
- Twenty's docs pages on workflow versioning and run logs weren't retrieved.

## 2. Salesforce Flow: record-triggered (before/after save), scheduled, platform event, scheduled paths, approvals, assignment rules

### Takeaway
Salesforce splits record-triggered automation into **before-save** ("Fast Field Updates", same-record field changes only, much faster) and **after-save** ("Actions and Related Records"). After-save flows can add **scheduled paths** (time offsets from a date field) and one **asynchronous path** (for callouts, run after the transaction commits). That split is the most transferable design idea for a Postgres engine.

### Cited Findings
- Before-save flows appear as "Fast Field Updates" and can only change the triggering record's own fields. After-save flows appear as "Actions and Related Records". One source says before-save runs "much faster (10 times)". — [salesforcetime.com, Before Save vs After Save (2022)](https://salesforcetime.com/2022/02/04/record-triggered-flow-before-save-vs-after-save/); [Automation Champion (2020/2022)](https://automationchampion.com/2020/12/15/getting-started-with-salesforce-flow-part-35-when-to-use-before-save-vs-after-save-record-triggered-flows/)
- Path types: an immediate path (before- and after-save), scheduled paths (after-save only, several per flow, labels renamable), and an asynchronous path (after-save, one per flow, needed for external callouts, because Salesforce blocks callouts while a record is saving). Async paths don't support ISCHANGED. — [Salesforce Help, record-triggered flow considerations (search summary)](https://help.salesforce.com/apex/HTViewHelpDoc?id=platform.flow_considerations_trigger_record.htm); [salesforcetime.com, Flow Trigger Explorer](https://salesforcetime.com/2022/04/17/flow-trigger-explorer/)
- Work on the Run Asynchronously path "does not begin until all work on the Run Immediate paths gets completed and those transactions are committed", so async sees the committed synchronous changes. — [Salesforce Help, considerations (search summary)](https://help.salesforce.com/apex/HTViewHelpDoc?id=platform.flow_considerations_trigger_record.htm)
- Flows can be triggered several ways (record-triggered, schedule-triggered, platform-event-triggered, screen and autolaunched). — [UnofficialSF, triggering flows](https://unofficialsf.com/pauple_helpie/triggering-flows/)

### Inferences
- **Map to a Postgres engine**: "before-save" means synchronous field derivations computed in the same transaction, either in app code or a `BEFORE` trigger. Examples are weighted amount = amount × stage probability, `stage_entered_at` on stage change, and normalising a domain. These must never call out or create other records. "After-save immediate" means outbox events written in the same transaction and consumed by workers right after commit. "Async path" means anything with an external call (Slack, email, webhook), always in a worker, always retryable and idempotent. "Scheduled path" means a job with `run_at` = date_field ± offset, re-evaluated when the date field changes.
- Salesforce's rule that async can't use ISCHANGED is a reminder that the event payload must snapshot the before/after values at commit time (store `changed_fields` and `old`/`new` in the outbox row), because the worker only sees current state.
- Approval processes (for example discount above X needs owner approval) and lead/case assignment rules are enterprise-shaped. For a few-user agency, approval is "a task assigned to the owner plus a status field that blocks the stage move", and assignment is the rotate-owner action.

### Gaps
- help.salesforce.com pages wouldn't render through the fetcher, so no first-hand read of the current Flow docs, the approval process docs (including the newer Flow Approval Orchestration) or assignment rules docs. The blog sources are 2020-2022, so labels and limits may have changed.
- Platform-event-triggered flow details and schedule-triggered flow batch limits weren't verified.

## 3. Automation engine design for a custom Postgres CRM (outbox, job queue, idempotency, delays, run logs)

### Takeaway
On Postgres, a durable automation engine can be built without Temporal. Write domain events into an outbox table in the same transaction as the record change, fan them out to a Postgres-backed job queue (graphile-worker or pg-boss, both `SKIP LOCKED` with retries and backoff), represent delays as jobs with a future run time, and record every run and step in your own log tables. Dedup keys give idempotency, and every external side effect must tolerate redelivery.

### Cited Findings
- **graphile-worker**: Node.js job queue on Postgres. LISTEN/NOTIFY gives "typically under 3ms" from scheduling to execution. A unique `job_key` prevents duplicate tasks. Automatic retries use exponential backoff, defaulting to 25 attempts over about 3 days. Crontab recurring tasks support optional backfill. Jobs in the same named queue run in series, otherwise in parallel. Jobs can be created inside the database from triggers or stored procedures, so "Postgres' transactional guarantees mean jobs aren't lost". It uses `SKIP LOCKED`. — [graphile-worker docs](https://worker.graphile.org/docs)
- **pg-boss**: built on `SKIP LOCKED`, with cron and RRULE scheduling, job deferral, queue policies for rate limiting/debouncing/concurrency, automatic retries with exponential backoff, dead-letter queues with redrive, pub/sub fan-out, and job creation inside an existing transaction (adapters for Drizzle, Knex, Kysely, Prisma). Requires PostgreSQL 13+ and Node 22.12+ or Bun. It promises "guaranteed atomic commits" but not exactly-once. — [pg-boss GitHub](https://github.com/timgit/pg-boss)
- **Twenty CRM workflows (open-source reference)**: triggers are record created, updated, deleted, "created or updated", manual (including bulk, which runs once with a list and needs an Iterator), scheduled, and webhook (GET/POST to a unique URL). Docs advise against plain "record created" for manually created records because the UI auto-saves before fields are filled. There's a soft limit of 100 runs/minute, and excess runs wait in "Not Started". — [Twenty docs, workflow triggers](https://docs.twenty.com/user-guide/workflows/capabilities/workflow-triggers.md); [Railway template page](https://railway.com/deploy/twenty-workflows--deploy-twenty-crm-workflows.md)
- Twenty actions: Create/Update/Delete/Search/Upsert Record, Pick Record (Random, Round Robin, Load Balanced), Iterator, Filter, Delay (duration or until date, no maximum, a past date fails the run), Send Email, Draft Email, Create Calendar Event, Form (manual triggers only), Code (JavaScript logic function), HTTP Request (30s timeout, 10 MB body cap), AI Agent and Classify. Search Records returns max 200 records. — [Twenty docs, workflow actions](https://docs.twenty.com/user-guide/workflows/capabilities/workflow-actions.md)
- HubSpot's own engine shows the hazards: a slow webhook gets executed and logged as failed, then retried, which "can lead to duplicate effects", and concurrent rotate actions are serialised with retries. — [HubSpot KB, troubleshoot workflow errors](https://knowledge.hubspot.com/workflows/troubleshoot-common-workflow-errors?no_head=1)

### Inferences (suggested design)
- **Tables**: `workflow` (id, object_type, status draft/active/paused) → `workflow_version` (immutable JSON graph of trigger + steps; activating creates a new version, and in-flight runs finish on their version) → `workflow_enrollment` (version_id, record_id, status running/waiting/completed/failed/unenrolled, enrolled_at, unique per (workflow_id, record_id) unless re-enrollment is allowed) → `workflow_step_run` (enrollment_id, step_id, attempt, status, input jsonb, output jsonb, error, started_at, finished_at). `domain_event` (outbox: id, object_type, record_id, event_type, changed_fields, old jsonb, new jsonb, actor_id, occurred_at, processed_at).
- **Flow**: the app writes the record and inserts a `domain_event` in the same transaction. A trigger or the app enqueues a `dispatch_event` job with `job_key = event_id`, which is idempotent. The dispatcher matches active workflow versions by object_type and trigger and creates enrollments, using the unique index for "enroll once". Each step is a job keyed `enrollment_id:step_id:attempt-group`. A delay step enqueues the next step job with `run_at`. "Delay until date property" stores the target, and an update to that property reschedules it (cancel and replace by `job_key`, which graphile-worker supports).
- **Idempotency**: internal DB actions run in a transaction that also marks the step done, so it's exactly-once internally. External actions (email, Slack, webhook) send an idempotency key (`step_run_id`) where the receiver supports one, and the system records "sent" before acknowledging. Accept at-least-once and make retries visible.
- **Loop protection**: changes made by a workflow carry `actor = workflow:<id>` on the domain event. Either skip self-triggering, or cap depth (for example 5 hops) and runs per record per hour. HubSpot's "go to action only within branches, prevents loops" is the same concern.
- **Date/"has not" triggers**: an hourly cron sweep job queries records matching a filter (close_date passed, no activity for N days, invoice overdue) and enrolls them through the same unique-enrollment path. This is how non-occurrence gets expressed, since events can't detect it.
- **Run log UX**: copy HubSpot's per-workflow action log and per-record "automation history" tab, which shows each step, its status, its error and a retry button. Keep 90+ days; at agency volumes, forever is fine.
- **Library choice**: for a TypeScript stack either works. graphile-worker has LISTEN/NOTIFY latency, `job_key` replace/dedupe, and add_job from SQL triggers. pg-boss has a built-in DLQ, debounce/throttle policies and ORM transaction adapters. At a few users, neither will be near its limits. Temporal or n8n isn't needed. n8n could still sit beside the CRM for long-tail integrations through outbound webhooks.

### Gaps
- n8n's execution and error-workflow model wasn't fetched this session.
- graphile-worker's exact SQL API (`graphile_worker.add_job(...)` with `run_at`, `job_key_mode`) wasn't confirmed on the fetched page. Check the docs' "add_job" page before implementing.
- No authoritative source was fetched for the transactional outbox pattern itself. It's presented as design inference.

## 4. Permissions: users, teams, seats, permission sets, record access, field-level, super admin (HubSpot, Salesforce) and Postgres RLS

### Takeaway
HubSpot's model is the right size for a small agency. Per object, each of View/Edit/Delete/Merge takes All, Their team's, Their own (owned only) or None, with an "include unassigned" toggle. Create is a separate toggle. Export, bulk delete and audit log access are separate admin toggles. Field-level view/edit restriction is Enterprise. Super Admin bypasses everything. Salesforce adds org-wide defaults, a role hierarchy and sharing rules, which is overkill for a few users. Postgres RLS can enforce the HubSpot model in the database.

### Cited Findings

**HubSpot**
- Super Admin has access to all tools and settings, except paid Sales/Service features that need a seat. Only a Super Admin can create another, and Super Admin permission sets can't be modified. Partner admin is similar but can't add/remove Super Admins or manage billing. — [HubSpot KB, user permissions guide](https://knowledge.hubspot.com/user-management/hubspot-user-permissions-guide)
- CRM object access: View, Edit, Delete and Merge each have a dropdown of **All / Their team's / Their / None**. "Their" means users see "only their assigned records on index pages, in the segments tool, and in reports". An **Unassigned** checkbox extends access to unowned records. **Create** is a separate toggle and doesn't govern records made by workflows, forms or integrations. **Communicate** (log email/call/meeting) has its own scope. — [HubSpot KB, user permissions guide](https://knowledge.hubspot.com/user-management/hubspot-user-permissions-guide)
- Admin toggles: Export, Export without approval, and Approve exports are separate. Bulk delete is separate from single-record delete. Audit log access, Security Center access, Modify billing and Permanently delete contacts are separate account permissions. Permission templates such as "Developer" exist as starting points. — [HubSpot KB, user permissions guide](https://knowledge.hubspot.com/user-management/hubspot-user-permissions-guide)
- Teams control sharing, and "Limit access by teams" lets users share assets. — [HubSpot KB, user permissions guide](https://knowledge.hubspot.com/user-management/hubspot-user-permissions-guide)
- **Field-level / sensitive data (Enterprise)**: Super Admins can set field-level permissions that restrict a property's view and edit access to specific users and teams. Super Admins keep access regardless. "Highly Sensitive Data" values are encrypted and must be clicked to decrypt. Form submission values marked sensitive are only visible to users permitted to view Sensitive Data. Configured under the property's "Manage access" tab. — [HubSpot KB, sensitive data in HubSpot tools (search summary)](https://knowledge.hubspot.com/account-security/sensitive-data-in-hubspot-tools?app=wp); [HubSpot KB, store sensitive data](https://knowledge.hubspot.com/properties/store-sensitive-data?y=0)
- Restricting edit access to properties exists per property, and editing property settings is itself a separate account permission. — [HubSpot KB, user permissions guide](https://knowledge.hubspot.com/user-management/hubspot-user-permissions-guide)

**Salesforce**
- Two layers. Permissions (Profile, Permission Sets, Field-Level Security) decide what you can do. Sharing (Org-Wide Defaults, Role Hierarchy, Sharing Rules, Manual/Teams/Apex) decides which records you see. Troubleshooting order: object permissions → FLS → OWD → role hierarchy → sharing rules/teams/manual. — [revenue.io, sharing and record visibility](https://support.revenue.io/guided-selling/salesforce-administration/user-management-and-permissions/sharing-records-and-record-visibility/); [Salesforce Developers blog, data security model explained visually](https://developer.salesforce.com/blogs/developer-relations/2017/04/salesforce-data-security-model-explained-visually)
- A user has one profile, one role, and many permission sets. Salesforce's guidance is to set OWDs to the most restrictive level and open access with roles, sharing rules and manual sharing. The role hierarchy grants vertical access (a manager sees subordinates' records) and needn't mirror the org chart. Sharing rules only extend access. — [Salesforce sharing cheatsheet](https://developer.salesforce.com/docs/atlas.en-us.salesforce_sharing_cheatsheet.meta/salesforce_sharing_cheatsheet/sharing_cheatsheet.htm); [Salesforce Developers blog](https://developer.salesforce.com/blogs/developer-relations/2017/04/salesforce-data-security-model-explained-visually)
- Salesforce recommends field-level security over just hiding fields on page layouts. — [Salesforce Developers blog](https://developer.salesforce.com/blogs/developer-relations/2017/04/salesforce-data-security-model-explained-visually)
- Conflict: one community source claims FLS "can only restrict, it cannot grant", while others say permission sets grant field access. The developer-blog view, where permission sets are additive and grant, is the reliable one. — [revenue.io](https://support.revenue.io/guided-selling/salesforce-administration/user-management-and-permissions/sharing-records-and-record-visibility/) vs [Salesforce Developers blog](https://developer.salesforce.com/blogs/developer-relations/2017/04/salesforce-data-security-model-explained-visually)

**Postgres RLS**
- `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`. With no policy the default is deny. `USING` filters existing rows for SELECT/UPDATE/DELETE, and `WITH CHECK` validates new or modified rows for INSERT/UPDATE (it defaults to the USING expression). Permissive policies OR together, and `AS RESTRICTIVE` policies AND together. Superusers and `BYPASSRLS` roles always bypass. Table owners bypass unless `FORCE ROW LEVEL SECURITY`. Policies run with the querying user's privileges, and security-definer functions can reach other tables. FK/unique checks bypass RLS. Policies that consult other tables can race under READ COMMITTED. `row_security = off` errors rather than silently filtering, which is useful for backups. — [PostgreSQL 18 docs, Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
- A common app pattern is `USING (owner_id = current_setting('app.user_id', true)::uuid)` with `set_config('app.user_id', ..., true)` per transaction. It's only as trustworthy as the app's connection handling. (The fetch summary describes this as general practice, not text from the Postgres page.) — [PostgreSQL docs page context](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

### Inferences (suggested model for a few-user agency)
- **Roles**: `owner` (super admin: billing, users, delete, export, audit log, settings), `manager` (all records, no billing or user admin), `account_manager` (view all, edit own plus unassigned, no delete or export by default), and optionally `viewer` or `contractor` (assigned records only). Store per-object scopes as `permission_set(object_type, action in view/edit/delete/merge/export, scope in all/team/own/none, include_unassigned bool)`. That's HubSpot's grid, and it's tiny to implement.
- **Field-level**: a `field_permission(field_id, role_id, can_view, can_edit)` table, used for a few sensitive fields (day rates, margin, cost price, contract value, personal data). Enforce it in the API layer (strip the field from responses, reject writes) because RLS is row-level only. Column privileges or views could add DB defence-in-depth.
- **RLS implementation**: one app DB role (not owner, no BYPASSRLS) for requests. Each request runs `SET LOCAL app.user_id/app.role/app.team_ids` inside its transaction. Each CRM table gets a permissive SELECT policy (`app.scope('deal','view') = 'all' OR owner_id = app.user_id OR (scope='team' AND team_id = ANY(...)) OR (include_unassigned AND owner_id IS NULL)`) and matching UPDATE/DELETE policies with `WITH CHECK`. Workers and workflows run under a separate role, either with explicit BYPASSRLS or a "system" identity, so automations aren't silently filtered. That matches HubSpot, where Create permission doesn't govern workflow-created records. Mark scope lookup functions `STABLE` and keep them simple for performance.
- Salesforce's role hierarchy, OWDs and sharing rules aren't worth building. "Team" scope plus an "Unassigned" toggle covers a 2-to-10 person agency. Note Salesforce's guidance to start restrictive and open up, but for a small agency the sensible default is view-all, edit-own.

### Gaps
- The HubSpot "restrict edit access to properties" URL 404'd. The field-level details come from the sensitive data page via search summary, so exact tier gating (Enterprise for view restrictions, possibly Professional for edit restrictions) wasn't confirmed first-hand.
- HubSpot seat pricing and seat types (Core/Sales/Service seats, 2025 pricing) weren't researched in this note.

## 5. Audit logs and field history (HubSpot, Salesforce, Postgres implementation)

### Takeaway
HubSpot's centralized audit log covers user-driven actions and logins. Login history shows 30 days in the UI and the API reaches about 90 days. It doesn't capture property changes made by forms, APIs or integrations. Per-record property history is separate. A custom build can easily beat this with a trigger-based audit table that records every change and its actor/source.

### Cited Findings
- The HubSpot Audit Logs page shows all logins in the last 30 days, including mobile. The developer docs say the login endpoint covers the past 90 days. — [HubSpot KB, account activity history](https://knowledge.hubspot.com/account-management/view-and-export-account-activity-history?authuser=0); [HubSpot developers, account audit logs API v3](https://developers.hubspot.com/docs/api-reference/account-audit-logs-v3/guide)
- The centralized audit log is limited to HubSpot-user actions. Property updates not made by a user (such as a form submission) don't appear, and community users note API and form changes are missing and that you can't filter by property or source. The legacy `propertiesWithHistory` API option works only for standard objects, not custom ones. Some features (the user analytics tab) need Enterprise. — [HubSpot KB, export account activity history](https://knowledge.hubspot.com/account/export-account-activity-history); [HubSpot community idea thread](https://community.hubspot.com/t5/HubSpot-Ideas/Report-on-Historical-Property-Values-Audit-Trail/idc-p/638104)
- HubSpot workflow action logs are retained for 90 days. — [HubSpot KB, workflow alerts/errors](https://knowledge.hubspot.com/workflows/understand-workflow-alerts-errors?app=1)

### Inferences (suggested Postgres design)
- An `audit_log` table (id bigserial, occurred_at, actor_type in user/workflow/integration/form/system/import, actor_id, source such as `workflow:<id>` or `api:<token>`, object_type, record_id, action in insert/update/delete/merge/export/login/permission_change, changed jsonb of `{field: [old, new]}`, request_id, ip). It's populated by a generic `AFTER INSERT/UPDATE/DELETE` trigger that diffs `to_jsonb(OLD)` against `to_jsonb(NEW)` and reads the actor from `current_setting('app.user_id', true)` / `app.actor_source`. Make it append-only: revoke UPDATE/DELETE from the app role and partition by month if it grows.
- Use it for three things HubSpot splits apart: per-record "field history" (when the stage changed and who changed it, which also feeds stage-duration and velocity reports), the account audit log (logins, exports, permission and role changes, workflow edits, deletes), and a "settings audit trail" (Salesforce's Setup Audit Trail idea) for pipeline, stage, field and permission configuration changes.
- Also keep a dedicated `deal_stage_history(deal_id, from_stage, to_stage, entered_at, exited_at, actor)`, since funnel and velocity reports depend on reliable stage timestamps (see section 6).
- Log exports and bulk deletes explicitly. HubSpot treats them as separate permissions, and for a small agency they're the main data exfiltration and loss risk.

### Gaps
- No first-hand fetch of Salesforce Setup Audit Trail (commonly cited as 180 days) or Field History Tracking limits (commonly cited as 20 fields per object, 18-24 months retention, Field Audit Trail add-on for longer). Not verified this session, so treat as unconfirmed.
- No source found stating HubSpot audit log total retention beyond the 30/90-day login windows.

## 6. Dashboards, reports and widgets: HubSpot builders, chart types, standard sales reports, forecasting, and what a small agency needs

### Takeaway
HubSpot's custom report builder sets the upper bound for a CRM report engine. It has a primary data source plus joined sources, dimensions and measures (up to 12 measures), about 12 chart types (bar, line, area, combo, donut/pie, KPI, gauge, scatter, pivot, table), ALL/ANY/custom AND-OR-NOT filters, a 1,000-row cap on charts and a two-hour refresh. Funnel reports on deal stages and "date entered stage" properties support conversion and velocity. For a small agency, a fixed set of about 10 well-built widgets beats a general report builder.

### Cited Findings
- **Custom report builder** (Professional/Enterprise in Marketing, Sales, Service, Data, Content and Revenue hubs; needs Create/own and Edit report permissions): pick a primary data source, toggle extra sources, filter by association labels. Datasets are Data Hub Enterprise only. Existing reports can't be merged. — [HubSpot KB, custom report builder](https://knowledge.hubspot.com/reports/create-reports-with-the-custom-report-builder)
- Dimensions are unaggregated (X-axis or "break down by"), measures are aggregated (Y-axis), up to 12 per report. Chart types: vertical bar, horizontal bar, line, area, combination, donut, pie, KPI, gauge, scatter, pivot table and table, plus "smart chart" recommendations. Field limits per chart: 12 Y fields for bar/line/area, 4 for combination, 30 for donut/pie/KPI/pivot/table, 1 for gauge. One event field per report. — [HubSpot KB, custom report builder](https://knowledge.hubspot.com/reports/create-reports-with-the-custom-report-builder)
- Filters match ALL, ANY or custom AND/OR/NOT groups. Some "not" conditions exclude records with empty values. Date filters use the account time zone. — [HubSpot KB, custom report builder](https://knowledge.hubspot.com/reports/create-reports-with-the-custom-report-builder)
- Limits: non-table reports are capped at 1,000 unique rows, while tables paginate. New data appears in 10-15 minutes. Reports auto-refresh every 2 hours, with manual refresh once per 15 minutes. Breakdowns with more than 99 values can't show on dashboards. — [HubSpot KB, custom report builder](https://knowledge.hubspot.com/reports/create-reports-with-the-custom-report-builder)
- **Funnel reports**: show stage-to-stage conversion for lifecycle stages, deal pipelines or custom event funnels. Standard funnels use the built-in Deal stage/Lifecycle stage properties, not custom ones. Intermediate stages can be optional, but the first and last can't. — [HubSpot KB, create custom funnel reports](https://knowledge.hubspot.com/reports/create-custom-funnel-reports?hc_location=ufi)
- **Velocity and forecast (third-party guidance)**: velocity uses HubSpot's auto-created "Date entered [stage]" properties, and deals predating stage changes may lack them. Days-in-stage is built in the custom report builder as an average grouped by stage. Weighted forecasts use "Weighted deal amount" (amount × stage probability), and default stage probabilities are placeholders that should be replaced with historical rates. AI forecasting is Sales Hub Enterprise. Funnel counts depend on reliable stage timestamps. — [Pedowitz Group, HubSpot pipeline reporting](https://www.pedowitzgroup.com/blog/hubspot-pipeline-reporting-blog); [Hublead, HubSpot funnel report guide](https://www.hublead.io/post/hubspot-funnel-report)

### Inferences (widget set and implementation for a small agency)
- **Priority widgets** (in order of use for an owner plus account managers):
  1. *Open pipeline value by stage*: a stacked bar or pipeline/kanban total, with count and sum per stage.
  2. *Weighted forecast this month/quarter*: sum(amount × stage_probability) for open deals with close_date in period, beside Won-to-date and target (a goal/quota line). Let the agency set stage probabilities, and show historical stage-to-won rates next to them so the placeholders get replaced, as the third-party guidance warns.
  3. *Win rate*: won / (won + lost) over deals closed in period, by owner and by lead source.
  4. *Average deal size* (won deals in period) and its trend line.
  5. *Sales cycle length*: median days created → won. Days in stage comes from `deal_stage_history` as an average/median bar by stage, the velocity view.
  6. *Stage conversion funnel*: deals entering each stage → next stage, built from stage history, not current stage, so skipped stages count (HubSpot's optional-stage concept).
  7. *Won/lost by reason and source*: bar or donut; lost-reason is the field agencies most often lack.
  8. *Overdue and due-today tasks per user*: a table and KPI, with rotting/stale deals (no activity in N days) as a table with links.
  9. *Activity leaderboard*: calls, emails, meetings and tasks completed per user per week. Low priority for 2-4 people.
  10. *Revenue invoiced vs paid vs outstanding (AR ageing 0-30/31-60/61-90/90+)*: needs the invoice/payment objects. For an agency this is arguably more important than sales activity metrics. Also *Won value vs invoiced* to catch won-but-unbilled work.
- **Dashboard mechanics worth copying**: dashboard-level filters (date range, owner, pipeline) applied to all widgets, per-user default dashboards, and KPI tiles with comparison to the prior period. The HubSpot limits (1,000 rows, 2-hour refresh) show that a small Postgres CRM can query live. Plain SQL views or materialised views refreshed on demand are enough at agency scale.
- **Report engine scope**: start with fixed widgets as SQL views (`v_pipeline_by_stage`, `v_forecast`, `v_win_rate`, `v_stage_durations`, `v_ar_ageing`), plus one simple "single-object report" builder: object, filters (ALL/ANY), group-by dimension, measure (count/sum/avg of a numeric field), and a chart type from bar, line, KPI, table, donut. Cross-object reports are the expensive part of HubSpot's builder and can wait. Salesforce's equivalent concepts are report types (an object plus related objects) and dashboard components (chart, gauge, metric, table), but they weren't verified this session.
- **Goals/quotas**: a `goal(user_id or team, metric, period, target)` table, rendered as a target line on the forecast and won widgets.

### Gaps

The velocity and forecast details come from third-party blogs.
- Salesforce report types (tabular/summary/matrix/joined) and dashboard components (chart/gauge/metric/table, dynamic dashboards) weren't verified this session because help.salesforce.com wouldn't render.
- Attio's reporting and permission model wasn't researched.
