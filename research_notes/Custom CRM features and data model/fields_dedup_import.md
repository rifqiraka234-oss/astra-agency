# CRM data management: custom fields, dedup and merge, manual creation, import/export, and Postgres custom field patterns

Research date 2026-11-06. HubSpot pages fetched directly from knowledge.hubspot.com unless marked "via search summary". help.salesforce.com pages are JS rendered and could not be fetched, so Salesforce facts below come from search summaries of Salesforce pages, Salesforce developer docs and third party guides, and are flagged as such.

## 1. HubSpot property settings (field types, groups, validation, conditional logic, calculations, history, sensitive data)

### Takeaway
HubSpot's property model is a small set of storage types (text, number, enumeration, date/datetime, bool) dressed in many "field types", plus per-property settings tabs for validation rules, conditional options, field-level access, sensitive data and documentation. Regex, conditional logic, calculation and property sync are paywalled (Pro/Enterprise), and up to 10 unique-value properties per object can only be set at creation. That's a good scope for a small agency CRM to copy.

### Cited Findings
**Field types and limits**
- Single-line and multi-line text: CRM entry capped at 65,536 characters (form submissions have no limit). Multi-line line breaks aren't supported in some tools such as marketing emails, quotes and sequences. — [HubSpot, property field types](https://knowledge.hubspot.com/properties/property-field-types-in-hubspot)
- Phone number: covers default phone/mobile/fax and custom phone properties, formatting and validation applied by country code. — [HubSpot, property field types](https://knowledge.hubspot.com/properties/property-field-types-in-hubspot)
- Single checkbox (true/false), multiple checkboxes (enumeration, multi-select, no custom sort), dropdown select (one value), radio select (one value, looks like a dropdown when editing a record). — [HubSpot, property field types](https://knowledge.hubspot.com/properties/property-field-types-in-hubspot)
- Enumeration limits: each option capped at 3,000 characters counting label, value and description, and a property is capped at 512,000 bytes or 5,000 options, whichever is reached first. — [HubSpot, property field types](https://knowledge.hubspot.com/properties/property-field-types-in-hubspot)
- Date picker and date and time picker. Date-time is shown in the viewer's device time zone on records while filters default to the account time zone. The updated form builder doesn't allow date-time properties. — [HubSpot, property field types](https://knowledge.hubspot.com/properties/property-field-types-in-hubspot)
- Number has four formats. Formatted (commas, over 20 digits shown in exponential notation), unformatted (treated as strings, keep to 38 total digits with up to 10 decimals for reliable reporting), percentage (stored as decimal, 75% stored as 0.75), currency (account default currency). Workflows and segments enroll on whole integers only. — [HubSpot, property field types](https://knowledge.hubspot.com/properties/property-field-types-in-hubspot)
- Calculation: computes values from associated record properties or custom equations, can't be used in forms, requires Professional or Enterprise. — [HubSpot, property field types](https://knowledge.hubspot.com/properties/property-field-types-in-hubspot)
- Rollup: aggregates across associated records, types Min, Max, Count, Sum, Average, output formats Formatted, Unformatted, Currency, Percentage, Duration. Tier not stated on the page. — [HubSpot, property field types](https://knowledge.hubspot.com/properties/property-field-types-in-hubspot)
- Property sync: copies a value from an associated record's property and keeps it updated, Pro/Enterprise. — [HubSpot, property field types](https://knowledge.hubspot.com/properties/property-field-types-in-hubspot)
- File: up to 10 files per property, record upload limit 20 MB free / 50 MB paid, forms 100 MB per file, viewing permissions set at creation. — [HubSpot, property field types](https://knowledge.hubspot.com/properties/property-field-types-in-hubspot)
- HubSpot user: holds one or more users, and selected users get owner-level edit permission on the record. Up to 250 per object, not usable in forms. — [HubSpot, property field types](https://knowledge.hubspot.com/properties/property-field-types-in-hubspot)
- URL: must be valid, "https://" added automatically, supports default link text and allow/block domain lists, not in forms. — [HubSpot, property field types](https://knowledge.hubspot.com/properties/property-field-types-in-hubspot)
- Rich text: bold, italic, colours, fonts, lists, links, images, max 64 KB per value including images, not in forms. — [HubSpot, property field types](https://knowledge.hubspot.com/properties/property-field-types-in-hubspot)
- Email property type: all domains, allowed domains only, or blocked domains, value must include "@". Can't be used as a recipient field for marketing or one-to-one email. — [HubSpot, property field types](https://knowledge.hubspot.com/properties/property-field-types-in-hubspot)
- A property can't be changed to Score or Calculation, and Score or Calculation properties can't be changed to another type. Changing text to dropdown creates one option per unique existing value, and type changes can invalidate existing values so HubSpot recommends exporting first. — [HubSpot, create and edit properties](https://knowledge.hubspot.com/properties/create-and-edit-properties)

**Internal name, groups, access, sensitive data, conditional logic**
- When editing an existing property you "cannot edit the property's object type or internal name". The label is edited in a Details tab, and a Documentation tab holds a description of how users should fill the value. — [HubSpot, create and edit properties](https://knowledge.hubspot.com/properties/create-and-edit-properties)
- Properties can be filtered by group (separate article on organising properties). — [HubSpot, create and edit properties](https://knowledge.hubspot.com/properties/create-and-edit-properties)
- A Manage access tab sets who can view and edit a property (e.g. everyone can view, only Super Admins edit). — [HubSpot, create and edit properties](https://knowledge.hubspot.com/properties/create-and-edit-properties)
- Sensitive Data tab requires Enterprise. — [HubSpot, create and edit properties](https://knowledge.hubspot.com/properties/create-and-edit-properties)
- Conditional logic requires Pro/Enterprise, and enumeration properties have a Conditional options tab (option sets that depend on another property's value). — [HubSpot, create and edit properties](https://knowledge.hubspot.com/properties/create-and-edit-properties)
- The Data sources tab shows which tools update the property. The custom property count is tier dependent, and a downgraded account can still edit existing custom properties but can't create new ones over the limit. — [HubSpot, create and edit properties](https://knowledge.hubspot.com/properties/create-and-edit-properties)

**Validation rules**
- Single-line text: no leading/trailing spaces, no spaces at all, custom regex, require unique, min/max character count, character restrictions (strip disallowed characters, numbers only, no symbols, uppercase only, lowercase only, title case). — [HubSpot, validation rules](https://knowledge.hubspot.com/properties/set-validation-rules-for-properties)
- Multi-line text: regex, unique, min/max chars, the same character restrictions. Number: unique, min value, max value, max decimal places. Phone: unique, validate formatting with optional default country code. — [HubSpot, validation rules](https://knowledge.hubspot.com/properties/set-validation-rules-for-properties)
- Date and datetime: any date, future only (any, after a buffer, rolling range in days), past only, specific range, Monday to Friday only. Date rules use the account time zone. — [HubSpot, validation rules](https://knowledge.hubspot.com/properties/set-validation-rules-for-properties)
- Validation rules exist on all plans, regex needs Pro/Enterprise. — [HubSpot, validation rules](https://knowledge.hubspot.com/properties/set-validation-rules-for-properties)
- Enforced on record editing (desktop and mobile), imports and new form editor submissions. NOT enforced in workflows, chatflows, meeting scheduling pages or legacy forms. The page does not say whether the API enforces them. — [HubSpot, validation rules](https://knowledge.hubspot.com/properties/set-validation-rules-for-properties)
- Rules apply to new or edited values only, existing values are not reformatted. Max 10 unique-value properties per object, settable only at property creation. Reusing the internal name of a deleted non-unique property for a new unique property errors. — [HubSpot, validation rules](https://knowledge.hubspot.com/properties/set-validation-rules-for-properties)

**Property history**
- On merge, property history from both records is combined. Secondary company domains don't appear in the Company domain name property history, which tracks only primary domains. — [HubSpot, merge records](https://knowledge.hubspot.com/records/merge-records); [HubSpot, multiple domains](https://knowledge.hubspot.com/records/add-multiple-domain-names-to-a-company-record)

### Inferences
- The minimum viable field definition row for a custom CRM, read off HubSpot: `object_type, internal_name (immutable, unique per object), label, description, group, field_type, display_format, options[] (label, value, description, order, hidden), validation (jsonb), is_unique (set only at creation), is_required, is_sensitive, view/edit roles, archived_at, created_by`.
- HubSpot's split of "storage type" from "field type" (radio and dropdown are both one-value enumerations, and number formats are display only) is a cheap way to give admins many choices without many storage paths.
- Calculations, rollups and property sync are the expensive parts. A small agency can push them to phase 2, or compute them as SQL views instead of stored values.
- Unique values settable only at creation is probably there because adding a unique constraint to a column that already has duplicates fails. A custom build hits the same wall, so it should check for duplicates before adding a unique index.

### Gaps
- Archived/deleted property restore window, "required properties" settings (HubSpot has per-pipeline-stage required properties and record-creation required properties, but neither page I fetched covered them), the score property type, and the full calculation function list were not on the pages fetched.
- Whether validation rules are enforced on API writes is not stated by HubSpot.

## 2. Salesforce custom fields: formula, roll-up summary, picklists, validation, history, record types

### Takeaway
Salesforce goes further than HubSpot on declarative logic (formula and roll-up summary fields, dependent picklists, global value sets, validation-rule formulas, record types and page layouts), but help.salesforce.com could not be fetched in this session, so most Salesforce specifics below rest on secondary sources and should be treated as medium confidence.

### Cited Findings
- Field history tracking: 20 tracked fields per object (standard and custom combined), data kept about 18 months in the UI and up to 24 months via API. Field Audit Trail (Shield add-on) raises it to up to 200 fields per object, kept until deleted. — [Gradient Works guide](https://www.gradient.works/blog/salesforce-field-history-tracking); [Salesforce Field Audit Trail Implementation Guide, Winter '27](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/field_history_retention.pdf) (via search summary)
- Roll-up summary fields can only be created on the master object of a master-detail relationship. One source puts the limit at 40 roll-up summary fields per object, and the older figure of 25 couldn't be confirmed. — [Traction Complete](https://tractioncomplete.com/articles/salesforce-rollup-summary-field-limitations/) (via search summary)
- External ID vs Unique: "External ID" marks a field usable for upsert matching, while "Unique" is a separate field-level constraint. Without Unique, upsert can still insert duplicates. — [Salesforce Help, External ID vs Unique ID](https://help.salesforce.com/s/articleView?id=000385174&language=en_US&type=1) (via search summary)

### Inferences
- Patterns worth copying from Salesforce for a small CRM. (a) Separate "external_id" flag on a field from "unique" flag. (b) Dependent picklists = HubSpot conditional options, stored as a map of controlling value to allowed option values. (c) Validation rules as boolean expressions evaluated server side, with an error message and the field to attach it to. (d) A shared global option set, reusable across fields (e.g. "Industry" on both company and deal).
- Record types and page layouts are probably overkill for a small agency. A single layout per object with field groups and per-field visibility covers it.

### Gaps
- Could not retrieve Salesforce's own docs on formula field return types, dependent picklist limits, global value set limits, validation rule syntax and record types/page layouts (help.salesforce.com returned only a JS shell). These need a browser render or the Salesforce PDF guides.

## 3. Deduplication: keys, auto-association, duplicate tools, merge behaviour, free-mail domains

### Takeaway
HubSpot dedups hard on one key per object (contact email, company primary domain, otherwise record ID or up to 10 custom unique properties), blocks duplicates on manual create, runs a daily fuzzy "potential duplicates" job for review, and merges with "primary wins unless empty" plus a list of type-specific exceptions. Merges can't be undone. Salesforce uses configurable matching rules (exact or fuzzy per field with thresholds) paired with duplicate rules (allow, alert or block), and merges at most 3 records at a time.

### Cited Findings
**HubSpot dedup keys**
- Contacts are deduplicated on Email. Manual creation with an existing email gets an "already exists" alert and is blocked. A form submission with a matching email updates the contact, and if submitted with a secondary email, that address replaces the primary. — [HubSpot, deduplication](https://knowledge.hubspot.com/records/deduplication-of-records)
- Companies are deduplicated on the primary Company domain name. Manual creation with a matching primary domain triggers an "already exists" alert. Imports match on primary AND secondary domains unless a custom unique ID is chosen. With no domain in a form, the contact's primary associated company is updated. — [HubSpot, deduplication](https://knowledge.hubspot.com/records/deduplication-of-records)
- Companies created via the API, including by third party sync apps, are NOT deduplicated by domain. — [HubSpot, deduplication](https://knowledge.hubspot.com/records/deduplication-of-records)
- Record ID works as the dedup key for all objects in imports. A blank Record ID creates a new record. Up to 10 custom unique-value properties per object, enforced on manual create/edit and imports but not in forms. — [HubSpot, deduplication](https://knowledge.hubspot.com/records/deduplication-of-records)
- If an import row matches multiple existing records, it fails with an error and is not imported. Rows with no identifier always create new records. — [HubSpot, deduplication](https://knowledge.hubspot.com/records/deduplication-of-records)

**Auto-association by email domain, free-mail, subdomains, multiple domains**
- HubSpot associates contacts with companies by matching the domain of the contact's Email to the company's domain. For common free-mail providers it instead checks the contact's Website URL, and if there isn't one, no match is made. — [HubSpot, auto-associate companies with contacts](https://knowledge.hubspot.com/object-settings/automatically-create-and-associate-companies-with-contacts) (via search summary)
- Each subdomain is treated as its own company (@example.com and @info.example.com give two companies). Up to 1,000 domains can be excluded, and removing one from the list means turning the setting off and on. Turning it on lets you choose whether to apply it retroactively. It does not override an existing association. If several companies share a domain, contacts go to only one of them, and you can't choose which. — [HubSpot, auto-associate companies with contacts](https://knowledge.hubspot.com/object-settings/automatically-create-and-associate-companies-with-contacts) (via search summary)
- Company domain should be entered as the root domain (example.com) without protocol, "www.", path or trailing slash. Secondary domains live on the same record. With auto-association on, contacts on any of the company's domains associate to it. Adding a domain that already exists on another company does not merge them. Imports can add "Additional domains" (semicolon separated) but cannot set the primary domain. No maximum count is stated. — [HubSpot, multiple domains](https://knowledge.hubspot.com/records/add-multiple-domain-names-to-a-company-record)

**HubSpot duplicate management tool**
- HubSpot re-compares records daily. By default it checks contact name, email, phone and zip, and company domain, name and country. Pairs can be merged or rejected one by one or in bulk. A bulk merge picks the survivor by rule (e.g. oldest or most recently updated). Rejections can be undone within 14 days, merges cannot. Data Hub Pro/Enterprise allows custom matching rules (up to 2 per object, up to 9 comparison properties). Managing individual duplicates needs Pro/Enterprise, and bulk caps are 30,000 pairs on Pro and 100,000 on Enterprise. — [HubSpot, manage duplicate records](https://knowledge.hubspot.com/records/manage-duplicate-records); [HubSpot, data quality tools](https://knowledge.hubspot.com/data-management/use-data-quality-tools) (via search summary)

**HubSpot merge behaviour**
- The record you open is the primary and survives. You can pick each property's value from either record, and by default the primary's value wins, with the secondary's used if the primary is empty. Create date becomes the older of the two. By default the merged record gets a NEW Record ID, old IDs searchable in "Merged [record] IDs" (a beta keeps the primary's ID). — [HubSpot, merge records](https://knowledge.hubspot.com/records/merge-records)
- Timeline activities and associations from both are combined (sync up to 30 min). For company "Primary" association labels, the primary company's keeps it. — [HubSpot, merge records](https://knowledge.hubspot.com/records/merge-records)
- Contact exceptions: the secondary's email becomes a secondary email, the furthest lifecycle stage is kept, conversions and forms submitted are summed, the most marketable status wins, the oldest original source is kept, legal basis takes the most recent, form submissions and cookies merged. — [HubSpot, merge records](https://knowledge.hubspot.com/records/merge-records)
- Company exceptions: the secondary domain becomes an additional domain, the furthest lifecycle stage is kept, and a merge fails if the parent-child hierarchy would loop. — [HubSpot, merge records](https://knowledge.hubspot.com/records/merge-records)
- Limits: a merge fails if the two records have 250+ combined prior merges or if the result would exceed association limits. Unmerge isn't possible (workaround is to remove the extra email/domain and recreate). Merge history is the "Merged [record] IDs" property, with who and when on hover, and bulk export of 90 days of merges, only for merges done in the Data Quality tool. Requires Merge permission or Super Admin. — [HubSpot, merge records](https://knowledge.hubspot.com/records/merge-records)
- Workflows: the primary stays enrolled and the secondary is unenrolled. Merged records don't enrol in new workflows from merge-driven data changes unless a setting allows it. — [HubSpot, merge records](https://knowledge.hubspot.com/records/merge-records)

**Salesforce**
- Matching rules do nothing on their own and must be paired with a duplicate rule, which sets the action (block, allow or alert). — [Salesforce Trailhead, Prevent Duplicate Data](https://trailhead.salesforce.com/content/learn/modules/sales_admin_duplicate_management/sales_admin_duplicate_management_unit_2) (via search summary)
- Fuzzy methods. "Fuzzy: First Name" uses Jaro-Winkler, Exact, Initials and Name Variant with a threshold of 85 (Johnny vs Johny scores 97). "Fuzzy: Last Name" uses Exact, Keyboard Distance and Metaphone 3 with a threshold of 90. "Fuzzy: City" is 85, "Fuzzy: Title" is 50. — [Salesforce Help, Matching Methods](https://help.salesforce.com/s/articleView?id=sf.matching_rules_matching_methods.htm&language=en_US&type=5); [Salesforce Help, Matching Algorithms](https://help.salesforce.com/s/articleView?id=sf.matching_rules_matching_algorithms.htm&language=en_US&type=5) (via search summary)
- Salesforce Help reports some name variants exceed the Jaro-Winkler threshold yet still don't match, because fuzzy first-name logic also uses pre-captured name patterns. — [Salesforce Help KB 000389625](https://help.salesforce.com/s/articleView?id=000389625&language=en_US&type=1) (via search summary)
- Rule count limits: sources conflict (up to 3 matching rules per duplicate rule and 5 active matching rules per object, versus 5 active duplicate rules per object). — [Trailhead](https://trailhead.salesforce.com/content/learn/modules/sales_admin_duplicate_management/sales_admin_duplicate_management_unit_2); contradicted by [Datalane](https://www.datalane.com/post/salesforce-duplicate-rules) (via search summary)
- Merge takes up to three records of the same type into one, deletes the others and reparents related records. The master's values win by default (in Apex, set values on the master before calling merge). In the UI you pick values side by side. Deleted merged records are visible via queryAll(). — [Salesforce Apex Developer Guide, merge](https://developer.salesforce.com/docs/atlas.en-us.234.0.apexcode.meta/pages/langCon_apex_dml_examples_merge.htm); [Salesforce API, merge()](https://developer.salesforce.com/docs/atlas.en-us.208.0.api.meta/api/sforce_api_calls_merge.htm) (via search summary)

**Pipedrive**
- On import you choose whether to merge detected duplicates or create new records. A person matches if ANY of organisation, phone or email matches, and an organisation matches on address. Merge tools cover deals, people and organisations, for admins or permitted users. — [Pipedrive, avoid duplicates during import](https://support.pipedrive.com/en/article/how-to-avoid-duplicates-during-an-import); [Pipedrive, merge](https://support.pipedrive.com/hc/en-us/articles/115001125925-How-do-I-merge-items-) (via search summary)

### Inferences
- Design for a small agency CRM: (1) hard unique keys, `lower(email)` on a separate `contact_emails` table (primary plus secondary emails, unique across the workspace) and normalised domain on a `company_domains` table (primary plus additional). (2) A blocking duplicate warning on manual create that links to the existing record. (3) A nightly or on-demand "possible duplicates" query using `pg_trgm` similarity on name plus exact phone/domain, with reject pairs stored so they don't resurface. (4) Merge = primary wins unless empty, per-field override in a side-by-side dialog, move all associations and activities, keep the losing IDs in a `merged_record_ids` table, and store a merge log with a JSON snapshot of the loser so that, unlike HubSpot, unmerge is at least manually possible.
- HubSpot's free-mail rule (fall back to the Website URL, else no company) is the safe default. Keep a free-mail domain blocklist table (gmail.com, outlook.com, etc.) that the admin can edit, and HubSpot's 1,000-domain exclusion list shows the expected scale.
- The HubSpot gap where API-created companies skip domain dedup is a warning: enforce uniqueness in the database (unique index), not in the UI layer only.

### Gaps
- The exact list of free-mail domains HubSpot uses was not found.
- Salesforce duplicate rule action options (block vs allow with alert/report, separate on create and on edit) are known from training knowledge but couldn't be confirmed from a fetched source this session.

## 4. Import and export

### Takeaway
HubSpot import is CSV/XLSX/XLS, one sheet, a header row, auto-suggested column mapping, create/update/both, matching on email/domain/record ID/custom unique property, multi-object files with associations, blank cells ignored (never clear values), semicolon separated multi-values, and error review per row. There is no single "undo import" button, only deletion of records an import created plus a 14 day CRM restore. Salesforce and Pipedrive both use "export with IDs, edit, re-import with ID column" as the bulk update pattern, and Salesforce adds upsert on a user-flagged external ID field.

### Cited Findings
- File types .csv, .xlsx, .xls, one sheet, header row matching property names in any order, fewer than 1,000 columns, UTF-8 for non-English characters. — [HubSpot, format import files](https://knowledge.hubspot.com/import-and-export/set-up-your-import-file)
- Limits (rolling 24h). Free tools 20 MB per file, 50 imports a day, 500,000 rows a day. Paid tiers 512 MB per file, 500 imports a day, 10,000,000 rows a day (80,000,000 via the imports API), 1,048,576 rows per file, 3 concurrent imports (2 can exceed 10,000 rows), extras queued. — [HubSpot, format import files](https://knowledge.hubspot.com/import-and-export/set-up-your-import-file); [HubSpot Imports API](https://developers.hubspot.com/docs/api-reference/latest/crm/imports/guide)
- Value formats. Dates DMY/MDY/YMD with / - or . separators, missing time defaults to midnight. Timestamps hh:mm or UNIX ms, offsets +hh:mm. Percent "25%" or ".25". Phone +[country][number] with "ext". Multiple checkboxes are semicolon separated with no spaces, options must already exist, and a LEADING semicolon appends instead of overwriting. Single checkbox True/Yes/False/No. Enumerations must match the label or internal value. — [HubSpot, format import files](https://knowledge.hubspot.com/import-and-export/set-up-your-import-file)
- Owners are mapped via an "[Object] owner" column using a name, email or internal value (email recommended), with no notification to assigned users. — [HubSpot, format import files](https://knowledge.hubspot.com/import-and-export/set-up-your-import-file)
- Blank cells are ignored, so existing values are never cleared by import. Clearing goes through bulk edit or a workflow. — [HubSpot, format import files](https://knowledge.hubspot.com/import-and-export/set-up-your-import-file)
- Associations: in one file, each row carries identifiers for every object, and you repeat a row to link one record to several. Missing identifiers create duplicates. Across two files, a common column links them. Association labels (Pro/Ent) are created first and go in an "Association label" column, with "Primary" setting the primary company. — [HubSpot, format import files](https://knowledge.hubspot.com/import-and-export/set-up-your-import-file)
- Single object import creates and/or updates one object. Multi-object import creates, updates and associates several objects in one file or two files. Emails/meetings/notes/tasks can be created but not updated. Record ID overrides other identifiers when mapped. Mapping is auto-suggested from header, header language and property name, with "Import as" to skip a column. The Mapping Guide checks up to 1,000 rows and some errors can be fixed during mapping. — [HubSpot, understand the import tool](https://knowledge.hubspot.com/import-and-export/understand-the-import-tool)
- Undo. From the imports dashboard you can delete records an import created, but updates made by an import can't be reversed that way. "Restore CRM changes" rolls back updates from workflows, imports or manual edits up to 14 days, selectable by import as the source. Deleted records are restorable from the recycle bin for 90 days. — [HubSpot, view past imports](https://knowledge.hubspot.com/import-and-export/view-and-analyze-previous-imports); [HubSpot, restore CRM changes](https://knowledge.hubspot.com/object-settings/restore-crm-changes) (via search summary). Third party sources conflict on the undo window (48h, 14d, 30d). — [operelio](https://operelio.com/templates/crm-import-limits), [vantagepoint](https://vantagepoint.io/blog/hs/importing-data-to-hubspot-best-practices-guide)
- Salesforce Data Loader upsert matches on an External ID field, or on the Salesforce ID when the object has no external IDs. Auto-number fields can't be used, and external IDs on related objects can populate lookups. — [Salesforce Data Loader Guide, Winter '27](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_data_loader.pdf); [Salesforce KB 000004514](https://help.salesforce.com/s/articleView?id=000004514&language=en_US&type=1) (via search summary)
- Pipedrive updates via export with "Pipedrive System ID" then re-import. Multi-option fields offer Overwrite or Append on import. — [Pipedrive, updating data with a spreadsheet](https://support.pipedrive.com/en/article/updating-pipedrive-data-with-a-spreadsheet) (via search summary)
- Twenty's CSV import does not create fields. Fields must exist first (Settings, Data Model), and import files should use API names rather than display labels. — [Twenty docs, migrating from other CRMs](https://docs.twenty.com/user-guide/data-migration/how-tos/migrating-from-other-crms) (via search summary)

### Inferences
- Import spec for the agency CRM: upload CSV/XLSX, then a preview of the first ~1,000 rows, then column mapping (auto-match on label/internal name, "skip", "create new field" inline), then the match key (email / domain / record ID / any unique field), mode (create only / update only / create and update), blank handling (ignore by default, optional "clear"), multi-select mode (overwrite / append). Run it as a job writing an `import_rows` table with per-row status and error, and give a downloadable error CSV with the original row plus an error column.
- Tag every created or updated row with `import_id`, and keep a before-image of updated fields in a change log. Then "revert import" can delete created records AND restore updated values, which beats HubSpot's partial undo and is cheap in Postgres.
- Export: export any saved view (current filters and columns) to CSV/XLSX, always including record ID, so the export → edit → re-import round trip works like Pipedrive and HubSpot.

### Gaps
- HubSpot export specifics (formats, limits, emailed link) not fetched. Salesforce Data Import Wizard limits (commonly 50,000 records) not confirmed this session.

## 5. Manual record creation

### Takeaway
HubSpot blocks a duplicate on manual create by email (contacts) or primary domain (companies) with an "already exists" alert, and enforces custom unique properties and validation rules in the create/edit UI.

### Cited Findings
- Manual contact creation with an existing email is blocked with an alert, and manual company creation with an existing primary domain triggers an "already exists" alert. — [HubSpot, deduplication](https://knowledge.hubspot.com/records/deduplication-of-records)
- Unique-value properties are enforced on manual create and edit. — [HubSpot, deduplication](https://knowledge.hubspot.com/records/deduplication-of-records)
- Validation rules are enforced on CRM record editing on desktop and mobile. — [HubSpot, validation rules](https://knowledge.hubspot.com/properties/set-validation-rules-for-properties)
- Attio exposes `is_required` per attribute ("a value must be supplied when creating a record") and `is_default_value_enabled` / `default_value`. — [Attio, attribute types](https://docs.attio.com/docs/attribute-types)

### Inferences
- The create form = all required fields plus admin-pinned "show on create" fields. A live duplicate check fires on email/domain blur (exact match) and offers "open existing" instead of creating. Quick-create from anywhere (e.g. company typeahead → "create company example.com") reuses the same endpoint, so DB-level unique constraints remain the backstop.

### Gaps
- HubSpot's "Manage create record form" settings and required-on-create configuration weren't on fetched pages.

## 6. Postgres implementation of user-defined custom fields, plus email/domain normalisation

### Takeaway
Three patterns. EAV (flexible, typed, but slow joins and bad planner stats), a JSONB column per record (one write, GIN indexable, the usual pragmatic choice), and real columns created by runtime DDL (Twenty's approach, with a metadata schema plus per-workspace Postgres schemas). Attio exposes a typed, historised attribute-value model. For a single-tenant small agency CRM, metadata tables plus a JSONB `custom` column, with expression indexes on hot fields, is the low-risk choice. Runtime DDL is viable if you want real column types and FK integrity.

### Cited Findings
**Twenty**
- Object and field definitions live as data in a `fieldMetadata` table in the core schema (`packages/twenty-server/src/engine/metadata-modules/field-metadata/field-metadata.entity.ts`) with a `type` column, a JSONB `defaultValue`, and a unique constraint on (name, objectMetadataId, workspaceId). — [Codeline repo review of Twenty (2024)](https://www.codeline.co/thoughts/repo-review/2024/twenty-open-source-crm)
- Each workspace gets its own Postgres schema `workspace_{uuid}`, managed by `workspace-datasource.service.ts`. A `WORKSPACE_SCHEMA_DDL_LOCKED` flag locks workspace DDL during hot upgrades. The GraphQL schema is assembled at runtime from cached object metadata, and the metadata API is separate from the workspace data API. — [Codeline repo review of Twenty (2024)](https://www.codeline.co/thoughts/repo-review/2024/twenty-open-source-crm)
- Trade-offs noted: the riskiest parts (dynamic schema assembly, workspace migrations) are the least test covered, and the custom `twenty-orm` layer on TypeORM is thinly documented. — [Codeline repo review of Twenty (2024)](https://www.codeline.co/thoughts/repo-review/2024/twenty-open-source-crm)
- Current field types in Twenty's shared enum: ACTOR, ADDRESS, ARRAY, BOOLEAN, CURRENCY, DATE, DATE_TIME, EMAILS, FILES, FULL_NAME, LINKS, MORPH_RELATION, MULTI_SELECT, NUMBER, NUMERIC, PHONES, POSITION, RATING, RAW_JSON, RELATION, RICH_TEXT, SELECT, TEXT, TS_VECTOR, UUID. — [twentyhq/twenty FieldMetadataType.ts (main)](https://raw.githubusercontent.com/twentyhq/twenty/main/packages/twenty-shared/src/types/FieldMetadataType.ts)

**Attio**
- 17 attribute types: actor reference, checkbox, currency, date, domain, email address, interaction, location, personal name, number, phone number, rating, record reference, select, status, text, timestamp. Every attribute has `is_multiselect`, `is_unique`, `is_required`, `is_default_value_enabled`/`default_value`, `is_archived`. Values carry `active_from` and `active_until` (null while active), so history is part of the value model, and most endpoints return only active values. — [Attio, attribute types](https://docs.attio.com/docs/attribute-types)

**Postgres JSONB indexing (primary docs)**
- The default GIN opclass `jsonb_ops` supports `?`, `?|`, `?&`, `@>`, `@?`, `@@`. `jsonb_path_ops` supports only `@>`, `@?`, `@@`, is "usually much smaller" and searches typically perform better, but can't answer key-exists queries and produces no index entries for empty structures like `{"a": {}}`. — [PostgreSQL docs, JSON types §8.14.4](https://www.postgresql.org/docs/current/datatype-json.html)
- Targeted expression indexes (e.g. `CREATE INDEX ... USING GIN ((jdoc -> 'tags'))`) "are likely to be smaller and faster to search than a simple index". Btree/hash on whole jsonb is only useful for whole-document equality. jsonb drops duplicate keys (last wins) and key order, and docs say most apps should prefer jsonb over json. — [PostgreSQL docs, JSON types](https://www.postgresql.org/docs/current/datatype-json.html)
- Practitioner sources: EAV writes are slow from row count and index churn, and JSONB consolidates many attributes in one write. EAV keeps an edge for B-tree sorting/grouping on a single attribute. A GIN index on JSONB only helps with indexable operators (containment etc.), so other query forms seq-scan. The usual hybrid is stable fields as columns, tenant fields in JSONB, and expression indexes like `((attrs->>'color'))` for hot fields. — [Raz Samuel, JSONB vs EAV](https://raz-samuel-blog.pages.dev/postgresql-jsonb-vs-eav-dynamic-data) (blog, medium confidence)
- A multi-tenant vendor on pgsql-general reports EAV with compound indexes "occasionally falls on its face" when the planner misjudges skewed statistics. — [pgsql-general, EAV Designs for Multi-Tenant Applications (2017)](https://www.postgresql.org/message-id/CAH7-FAsLYDK3Jy9GN3%3DhY6w%3D2N%3D0CkGW9KmMgKafPx3PGOEDqw%40mail.gmail.com)

**Email/domain normalisation**
- `citext` compares by lowercasing both sides, and the Postgres manual now suggests considering nondeterministic collations instead. Nondeterministic ICU collations handle case-insensitive and accent-insensitive comparison and more Unicode cases correctly. — [PostgreSQL docs, citext](https://www.postgresql.org/docs/13/citext.html); [Postgres Pro 18 citext](https://postgrespro.com/docs/postgrespro/18/citext.html)
- A plain unique constraint on text is case sensitive, so the common pattern is a unique B-tree index on `lower(email)`. — [Postgres.FM transcript](https://share.transistor.fm/s/98d031a2/transcript.srt) (via search summary)
- An open pgsql-bugs report (BUG #19646, 2026-08-29) says a unique index with an explicit different COLLATE can bypass a nondeterministic collation's equality. Unresolved as reported. — [pgsql-bugs #19646](https://www.postgresql.org/message-id/19646-b1cfc299badcbd7e@postgresql.org)
- HubSpot's own convention: the company domain is the root domain without protocol, www, path or trailing slash, and subdomains are treated as separate companies for auto-association. — [HubSpot, multiple domains](https://knowledge.hubspot.com/records/add-multiple-domain-names-to-a-company-record)

### Inferences
- Recommended small-agency schema:
  - `field_definitions(id, object_type, internal_name, label, description, group_id, field_type, display_format, options jsonb, validation jsonb, is_required, is_unique, is_sensitive, default_value jsonb, position, archived_at, created_at)` with `unique(object_type, internal_name)`, and `field_groups`, `option_sets` (global value sets) alongside.
  - Records keep core columns (name, email, domain, owner_id, timestamps) as real columns, with `custom jsonb not null default '{}'` keyed by `internal_name` (never by label, so renames are free).
  - Validate in the app layer from `field_definitions` (type, min/max, regex, options) on every write path: UI, import and API. Optionally add a trigger that rejects unknown keys.
  - Index with one `GIN (custom jsonb_path_ops)` for equality/containment filters, plus btree expression indexes such as `((custom->>'industry'))` or `(((custom->>'deal_size')::numeric))` created when an admin marks a field "filterable/sortable". Unique custom fields get a partial unique expression index created at field creation time, after checking existing data for duplicates (which mirrors HubSpot's "unique only at creation").
  - Field history: a generic `field_changes(record_type, record_id, field, old jsonb, new jsonb, source, source_id, changed_by, changed_at)` table, written from the app or a trigger. This gives HubSpot-style property history, import revert and merge audit in one place.
- Runtime DDL (Twenty style) gives real types, FKs for relation fields and normal btree stats, but needs a migration runner, locking and cache invalidation. Twenty itself flags it as the riskiest, least-tested part. For one workspace with a few dozen custom fields, JSONB is simpler. Move a hot custom field to a real column later with a generated column or a one-off migration.
- EAV is only worth it if per-value history (Attio's `active_from`/`active_until`) is a core requirement. Even then, a JSONB current-value column plus a history table gets most of the benefit.
- Normalisation functions to build in: email `lower(trim(email))`, unique index on the normalised value (or a nondeterministic ICU collation column, while watching bug #19646). Domain: strip scheme, `www.`, path, port and trailing dot/slash, lowercase, IDN to punycode, then reduce to the registrable domain with the Public Suffix List (so `foo.co.uk` and `shop.foo.co.uk` resolve sensibly). Store both raw and normalised. Keep an editable free-mail blocklist so gmail.com etc. never create or match companies.

### Gaps
- No primary source fetched for the Public Suffix List or a Postgres PSL extension. Implementing it in app code (e.g. a `tldts`/`psl` library in Node, `publicsuffix2`/`tldextract` in Python) is the usual route, but this wasn't verified this session.
- Twenty's composite-field column layout (e.g. CURRENCY as amountMicros + currencyCode, select as Postgres enum) and whether Twenty still uses per-workspace schemas in late-2026 releases could not be confirmed from source (GitHub API access was not enabled, and the architecture source is a 2024 review).
- Attio's internal storage and its assert/upsert `matching_attribute` behaviour: the docs page returned 404 and wasn't confirmed.
